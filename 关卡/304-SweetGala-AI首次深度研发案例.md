1. 检查棋盘是否落满 → 落满弹 Grand JP 弹板

4. 所有金饼结算完成 + win 框翻滚停止 → 弹出结算弹板
5. 关闭结算弹板 → 转场动画 → 回到 Base 玩法

- **坐标翻转工具方法**：`flipCellRow(backendId, rows)` / `flipMultiData(multiData, rows)`，并自行决定在 `applyLineVisibility` / `getRegionBorderNodes` 使用点而非数据源做翻转（保留原始后端数据）
- **区域中心计算**：`getRegionCenterWorldPos` 通过对区域内 cell 位置求平均得到
- **结算排序的复合 comparator**：col 第一 / row 第二（反向，因后端坐标系）/ index 第三
- **奖金计算的区域倍数注入**：`getCellRegionMulti` + `regionMulti` 字段，金币与 JP 两路径均生效
- **5 个 Action 的差异化**：red 全量替换、blue/purple 单纯加动画、purple 还要判 `reTriggerColors.indexOf(0)` 首触发条件

**模式提炼（与其他样本的关键差异）**：

- **长链路功能流的 AI 实现范式**：人类提供 5 步骨架 + AI 落地 + 人类 17 轮微调，每一轮都是局部修正，不会触发整体重写。
- **跨切关注点的早期发现至关重要**：第 3 条反馈"后端 row 反向"是隐藏的不变量，应该在**任务起步**就抽出独立工具方法，否则每个使用点都要手动翻转，AI 容易遗漏（fl 实际确实出现遗漏，靠人类 review 发现）。
- **API 简化反馈出现频率高**：第 6、14 条都是"简化 / 别绕弯"。AI 倾向于"防御性多步推导"（如先从 `bonusList` 构造 `landedSet` 再判满），人类倾向于"直接使用已有真值（`blueArea[k].values()` 全 true）"。
- **横向扩展请求扎堆**：第 15、16、17 条三连击——一类动画需要在 3-4 个 Action 中复制实现，AI 应主动提议**抽出基类方法**，否则代码会冗余。
- **业务变体差异要在 prompt 里前置说明**：紫色与红/蓝在 trigger 动画播放条件上存在差异，若不在第 16 条统一指令中说明，第 17 条返工不可避免。

**Context 耗尽事件 — 304 全程唯一一次**：

- 原始会话在执行到样本 D / E（蓝色区域 console 报错）之前被 compact
- compact 后的 280 行结构化摘要被自动注入 `10df40a5` 续接，包含：1) 全部已变更文件 + 关键代码片段；2) 17 条用户消息原话；3) 4 个错误及修复记录；4) 当前进度状态。
- **若没有 compact 摘要机制，整个 Link 结算流程的上下文将完全丢失**，下次需求人类要从头解释，AI 也无法保持设计一致性。

**经验**：当单一会话预计涉及 ≥ 3 个文件协调修改、或 ≥ 10 轮反馈时，**应主动在中段写入 docs**（不依赖 compact），把"已固化的设计决策"（如 CORNER_CELLS 映射、排序规则、命名规约）落到本案例文档对应章节，作为下次会话的快速预热材料。

### 样本 F：蓝色区域分割与倍数节点设计（2026-05-07，会话 `1383130a`，**AI 独立完成的模块**）

> 这是 304 全程**最特殊的一个会话**：任务为纯抽象算法 + 模块设计，人类**没有提供任何参考代码**，且明确说"**不需要读代码**"。AI 从零设计了数据结构、变量命名规则、API 形态，最终落地为 `SweetGalaMachineScene304.applyMultiplierNodes / getMultiplierNodeList` + `SweetGala_TriggerBlueGameAction.initMultiplierNodes`，对应提交 `486a44f08`。

**任务原文（人类第 1 条实质性消息）**：

> 给你一个 3 行 5 列的格子。从左上为第 0 个格子，往下为第 1 个格子再往下为第 2 个格子，然后第二列最上边是第 3 个格子。
>
> 现在要把这些格子分为 4 个区域。每个区域内部肯定相邻，比如第一个区域为 `{0,1}` 里面表示格子 ID。不会出现 `{0,2}`，因为这两个不相邻。
>
> 这些格子相邻的地方都有一个线。用来表示区域。比如 `{0,1}` 那么格子 0 和格子 1 中间的线需要隐藏起来。格子 2 和当前区域不是同一个，那么格子 1 和格子 2 中间的线需要显示出来。**请设计怎么表示中间的线，怎么计算和显示。给出代码和中间线的绑定变量名。**

**13 条人类消息的演化路径**：

| # | 人类消息 | 性质 |
|---|---|---|
| 1 | "不需要读代码" | 设定边界：纯设计 |
| 2 | 抽象问题描述（上方原文） | 给出完整需求 |
| 3 | "外边一圈也需要处理" | 边界扩展 |
| 4 | "内部线不要 V 和 H 是不是代码会更简单一些，这样会有问题吗" | **反向质疑 AI 方案** |
| 5 | "不是每个格子的角落，是 4 个角。表示这个区域的倍数" | 语义澄清 |
| 6 | "不是某个区域的四个角，是整个大的轮盘 4 个角，一个角放一个倍数" | **再次澄清——同一术语两层歧义** |
| 7 | "多用几组数据验证，看看会有问题吗" | 强制 AI 自测 |
| 8 | "每个角落的 cell 一定不会在一个区域呢，0 2 12 14 一定是分别在 4 个区域内" | 给出业务不变量 |
| 9 | "controller 换成外部传入吧，是直接传入节点，并且传入每个倍数区域的颜色，这样好看，这样可以设置节点下边的 bg 颜色 也可以设置节点下边的文本倍数" | API 形态重构 |
| 10 | "还可以优化吗" | 抛光 |
| 11 | "是不是可以优化一下" | 抛光 |

**AI 独立产出**（最终落地到代码）：
- **内部线表示策略**：水平线 / 垂直线绑定到格子的相对位置，AI 自主选择命名约定
- **外圈线处理**：补全 4 周边界
- **倍数节点选址算法**：`bl / tl / br / tr` 4 个角各放一个，从 4 个区域里各挑一个角格作为锚点（即 `[2, 0, 1, 3]` 这种区域索引到角位的映射）
- **对外 API 形态**：`applyMultiplierNodes(nodes, colors, multipliers)` 由 Action 注入，Scene 只负责显示

**模式提炼**：
- **纯算法委派的边界条件**：必须是逻辑闭合的子问题（区域 / 网格 / 状态机），不依赖关卡其他流程语义。
- **AI 自主命名权**：在没有现成参考时，AI 可以决定变量命名（如 `_baserespinCount` 后期接入时仍走人类提供的现成命名）。设计阶段 AI 主导，集成阶段人类提供既有命名。
- **歧义高频出现**："角"在用户表述里出现 2 次不同含义（每格 4 角 / 整盘 4 角），"格子"和"区域"边界容易模糊。AI 应主动澄清而非默选其一。
- **必须强制多数据自测**："多用几组数据验证，看看会有问题吗"是该会话的关键转折点——AI 设计完成后，**业务不变量驱动的回归测试比单元测试更重要**（如"4 个角格一定分属 4 个区域"）。

## 三、Human & AI 交互模式总结

### 3.1 七类有效 Prompt 范式

| 范式 | 使用场景 | 模板 | 代表样本 |
|---|---|---|---|
| **锚点引用** | 修改既有逻辑 | "节点是 `this.mainUIComponent.getMainUINode("_baserespinCount")`" — 给方法/节点名 | D |
| **横向参考** | 新功能实现 | "可以参考 297 关卡的 simulateReels" — 指向另一个关卡 | A |
| **结构化调研** | 大范围搜索 | "在 X 目录搜索 Y，关注 Z，返回 W" — 适合派生 subagent | B |
| **现场调用栈** | 运行时报错 | 直接粘 console / stack trace | E |
| **反向 review** | 收尾抛光 | "有没有可以优化的地方？" / "for 循环的地方不优化吗" | A · B · F |
| **纯抽象委派** | AI 独立模块设计 | "不需要读代码 / 给你一个 X，需要做 Y / 给出代码和绑定变量名" | **F** |
| **长链路骨架 + 微调** | 跨多文件功能流实现 | "完善当前脚本流程：1) … 2) … 3) …" + 17 轮微调 | **G** |

> 范式 6（纯抽象委派）是 304 期间**唯一一次** AI 完全主导设计的案例。其触发条件：**子问题逻辑闭合 + 不依赖关卡其他语义 + 可由业务不变量验证**。下一关卡接入时，所有「网格 / 状态机 / 区域分割 / 路径搜索」类子任务都可以走该范式。

### 3.2 AI 误操作 6 大典型（与规避手段）

| 误操作 | 案例 | 规避手段 |
|---|---|---|
| **过度删除** | 计数器恢复显示逻辑被当冗余移除 | Prompt 显式声明"**保留原有 X 的行为，只新增/替换 Y**" |
| **业务术语混淆** | 「轴」与「列」混用导致 +6 步规则错位 | 首句给出术语字典：1 列 = 3 个轴，两列间 = 2 步 |
| **边界范围错位** | "差一个就满"被误读为子区域而非全盘 | 明确范围量词：**整个轮盘 15 个位置** |
| **盲改不解释** | 清理 drum 动画顺序未交代理由 | 要求 AI "**先解释为什么这么做，再改**" |
| **防御性多步推导** | 从 `bonusList` 构造 `landedSet` 再判满（实际 `blueArea` 已有真值）；红色玩法遍历所有 cell 找匹配（实际 `redBonusList` 已是答案） | "**直接使用 X，不要绕**" / Prompt 提供已有真值字段名 |
| **横向扩展时遗忘业务变体** | 红/蓝/紫 trigger 动画三连击，紫色实际只首次播 | Prompt 同时声明 N 个对象的**相同点与差异点** |

### 3.3 测试反馈闭环

实机测试发现的**进出场 / 重连 / 首进**场景，AI 难以主动想到，必须由人类回放触发：

- ReSpin 退出后计数器残留
- 首次进入关卡的初始可见性
- 断线重连场景（在 `51144b80b` 中专项处理）

> **规范**：每个关卡 Action 提交后必须由人工在 **首进 / 触发玩法 / 退出玩法 / 断线重连** 四条路径上回放，并作为下一轮 AI 输入的现场报告。

## 四、AI 关卡研发规范（v1.0）

### 4.1 任务委派规范

| 任务类型 | 主导方 | AI 角色 | 304 实例 |

## 五、风险与规避清单

> 下表是 304 期间出现过且**已经付出代价**的真实风险，强烈建议下一个关卡开局前过一遍。

| 风险 | 触发条件 | 304 实例 | 规避手段 |
|---|---|---|---|
| AI 删掉承载业务约束的代码 | 任务为"重构 / 优化" | 计数器恢复显示被删 | Prompt 必须说"保留 X" |
| 业务术语混淆 | 关卡有自定义术语 | 「轴 / 列」混用 | 任务首句给术语字典 |
| 边界范围理解错位 | 涉及"差一个"等模糊量词 | 蓝色区域 vs 整盘 15 格 | 用绝对数字代替相对描述 |
| 复杂逻辑分支遗漏 | 玩法有 super / normal 双形态 | 普通 ReSpin 与 Super ReSpin | 强制在 init/show/hide 三态分别处理 |
| 实机场景遗漏 | 涉及流程退出 / 重连 | ReSpin 退出计数器残留 | 四路径回放规范（4.3 节） |
| AI 自我陈述与实际差异 | AI 报告"已完成" | 「改完没问题」实际仍残留 | 提交前必须实机回放 |

| **跨切关注点的延迟抽象** | 同一不变量在 N 处使用 | 后端 row 反向，初期每处手动 flip | 不变量声明的**第一时刻**就抽工具方法（如 `flipCellRow`），人类要主动追问"还有哪些地方要 flip" |
| **多对象横向扩展时漏掉变体** | "X 也加 / Y 也加" 三连击 | 红/蓝/紫 trigger，紫色只首触发 | 横向扩展请求必须**列出所有差异点**而非"和 X 一样" |

## 六、关键工具与基建支撑

### 6.1 SlotAction 模式
304 完全遵循 [SlotAction 优化记录](/关卡/SlotAction-优化记录) 中确立的"每玩法一 Action"拆分，使得 AI 在跨关卡迁移时可以以**单 Action 文件**为复制粒度，例如 `SweetGala_SlowDrumModeAction.js` 可由其他关卡的 `SlowDrumModeAction` 派生。

### 6.2 git-commit skill
位于 `.claude/skills/git-commit/`，提交时自动调用 `/code-review`，对 AI 改动做风险评估。304 后期 12 次提交的标题规范度均高于前 6 次，正是该 skill 的产物。

### 6.3 子 agent 并行调研
样本 B 中单会话调用 12 次 Task 工具，并行委派 Explore / general-purpose 子 agent 进行跨目录搜索，避免主上下文被大量 Read 结果污染。这是后续大型关卡调研的推荐范式。

### 6.4 项目内 OpenSpec
对于跨关卡的玩法抽象（如 SlowDrumMode 在 Base 中的通用规则），应该通过 `openspec/` 创建提案而非直接散落在某一关卡代码内，否则下一个关卡接入时 AI 难以发现。
