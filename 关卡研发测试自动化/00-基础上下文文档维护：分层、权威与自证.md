# 基础上下文文档维护：分层、权威与自证

> 源自飞书文档 · 最后同步：2026-09-11

> 当项目里出现 `AGENTS.md` / `CLAUDE.md` 这类「给 AI 的规则文件」，它会在几个月内长成一份没人敢删、AI 也执行不动的杂物间。

> 本文给出四条判据，回答同一个问题：**这条规则该写在哪一层？** 附一次完整治理的前后数据与可直接复用的规则、Skill 全文。

---

## 〇、样本背景（读案例前先看这个）

后文所有案例出自两个真实仓库。案例的价值在于「哪一类内容错放了哪一层」，与它们具体是什么项目无关，因此一律以角色名指代：

| 角色名 | 是什么 | 规模 |
| --- | --- | --- |
| **工作区仓库** | 个人的多用途工作区，一个仓库里同时放着计划文档、自建工具、AI 任务定义、配置。根目录有一份 `AGENTS.md` 作为全仓库规则入口 | 治理前 181 行 |
| **业务仓库** | 一个独立的商业项目仓库，与工作区仓库无从属关系。它有自己的 `.claude/skills/` 本地技能目录 | — |

工作区仓库里被反复提到的下游承接点，也用角色名：

| 角色名 | 实际是什么 |
| --- | --- |
| **文档网关工具** | 封装某云文档平台 API 的自建 CLI，是该平台读写的唯一入口 |
| **工作流执行器** | 编排多步骤任务的自建 CLI |
| **插件宿主** | 一个本地插件平台，下挂十来个自写插件 |
| **云文档平台** | 团队用的在线文档产品（Confluence / Notion / 飞书一类） |
| **定时任务平台** | 一个带定时调度面板的桌面 AI 客户端 |

**这张表不用记。** 读到案例时只需问一句：这类内容，该落在哪一层？

## 一、痛点

### 1.1 表层症状：规则文件在腐烂

`AGENTS.md` 这类「给 AI 的规则文件」有一个共同的失败模式：不受控地长大，并逐渐失去可执行性。

工作区仓库的 AGENTS.md 在治理前是 181 行，里面混着五类内容：

| 类型 | 实例 |
| --- | --- |
| **历史事件** | 「个人笔记已迁至云文档平台，不在本仓库」 |
| **现状快照** | 「当前活跃的 AI 任务」表，逐条列出 5 个任务 |
| **实现细节** | 本地服务端口号；十来个插件名逐条枚举；第三方 API 的枚举值与列宽算法 |
| **双份权威** | 某工具的规范一节自己写着「详细版见 README；本节是权威摘要」 |
| **失效指针** | `.gitignore` 注释指向「AGENTS.md 第四节」，而章节早已重排 |

共性是：**写下的那一刻是对的，此后无人维护，逐日腐烂**。执行者读到它们，要么被过期信息误导，要么在正文与 README 的两份说法之间无所适从。

### 1.2 深层病灶：缺的不是「写不写」，是「写在哪一层」

第一轮体检时，已有一份 `maintain-agents-md` 规范，它给出了「三职能准入」（约束 / 默认 / 路由）和「两条硬约束」（面向未来 / 实现无关）。但用它做出来的建议被逐条驳回：

| 建议 | 为什么错 |
| --- | --- |
| 删掉「已迁至云文档平台」 | 它字面是历史，**隐含的是路由约束和入库约束**。直接删会连约束一起丢失 |
| 把某个单一子目录下工具的规则写进该目录通则 | 只约束单个工具的规则，**不该占用根层预算** |
| 把 `.gitignore` 规则解释一遍写进 AGENTS.md | 机制**已由系统强制**，规则文件复述无价值 |
| 把 git 提交纪律写进 AGENTS.md | 这是**跨仓库通用**的工作方法，不属于任一仓库 |

四条驳回指向同一个缺口：**规范只有「写不写」的判据，没有「写在哪一层」的判据**。

而且诊断本身也错了——真实行数 181，在 200 行预算内。**按旧规范体检，结论是「合格」**。病灶根本不是体量，是分层错位。这说明旧规范会给出误导性的通过结论。

### 1.3 第三个坑：规范自己没过自己的体检

治理到中途，用规范反查规范本身，发现它的「权限与能力」一节内嵌了完整的 JSON 响应体（操作列表、权限位、检查时间戳）——而它自己的硬约束写着「移除端口路径与字段名，只留指针」。

**规范文件本身违反了自己定义的规则。**

### 1.4 第四个坑：自动迭代一条建议都没采纳

这类 Skill 通常带自我迭代机制（使用反馈 + 改进建议 + 基准检查 → 编译新版本 → 在 benchmark 上 A/B 验证）。但翻查全部迭代记录：**连续四轮，采纳的建议数全是 0**。期间提交的四条改进（含关键的「优先级与让位」判据）从未进入任何版本。

同时质检状态长期卡在 `proven: 0`。根因是**语言错配**：正文被编译成英文，而基准断言是中文。断言按文本包含判定、不跨语言匹配，所以**全挂**。

横向对照坐实了这一点：同期建的另两个 Skill 都是中文正文配中文断言，质检全部通过。唯一的变量就是语言。

更荒谬的是：该 Skill 的描述字段是中文，正文却是英文——**同一个 Skill 内部就不一致**。

## 二、采用的手段

### 2.1 手段一：补上「层级归属」判据

一条规则写在它所约束范围的**最小闭包**处：

| 约束范围 | 归属 |
| --- | --- |
| 只约束单个目录或工具 | 该目录的 `README.md` |
| 跨多个目录但仅本工作区成立 | 根 `AGENTS.md` |
| 跨仓库通用的工作方法 | Skill 或中央知识系统，根文件只留指针 |

图 1 · 规则层级归属：一条规则写在它的最小闭包处　交互版：[https://ghoststudio.feishu.cn/file/IzMcbse1yoT4bqx6amxcpYGonsg](https://ghoststudio.feishu.cn/file/IzMcbse1yoT4bqx6amxcpYGonsg)

**派生禁令**：同一条规则只能有一处权威。禁止「本节是权威摘要」式的双份权威——摘要必然与正文漂移，届时执行者读到哪一份就照哪一份执行。

### 2.2 手段二：补上「优先级与让位」判据

层级归属解决了「该写在哪」，但没解决「两层同时存在时谁生效」。这个缺口在实践中立刻暴露了：起草一条全局的 git 提交纪律时，发现**业务仓库**已有自己的本地 git 技能文件，且其中明写 `git add .`——与全局规则直接冲突。

判据：

- **就近者胜**：所在仓库的规则或本地 Skill 与全局冲突时，以就近方为准
- **全局规则必须自带让位声明**，明确写出「下层另有规定时以下层为准」
- **覆盖必须是有意的**：遇到矛盾先判断是刻意差异还是下层陈旧未同步。陈旧的应当修下层，不默认让它胜出
- **新建全局规则前先扫描下层同名规则**，避免以全局姿态压在每个仓库头上
![](/feishu/基础上下文文档维护：分层、权威与自证/00-基础上下文文档维护：分层、权威与自证/img-2.png)

图 2 · 优先级与让位：两层同时存在时谁生效　交互版：[https://ghoststudio.feishu.cn/file/Dqgfb2UUso49M4xz23gcNKE3n4e](https://ghoststudio.feishu.cn/file/Dqgfb2UUso49M4xz23gcNKE3n4e)

这条判据的实际应用：给全局规则加上带出口的写法（「仓库已有明确产物忽略清单且 `.gitignore` 与之一致时，可用 `git add .`，但必须 `git status --short` 逐条核对」）。业务仓库恰好满足该例外，**无需改动任何东西**。

顺带发现业务仓库内部自身已矛盾：其本地技能文件写「即使用户说『提交吧』也必须二次确认」，而它自己指向的权威文件写「该指令即授权自动执行，不再请求二次确认」。前者是陈旧副本——正是「陈旧应修下层」的实例。

### 2.3 手段三：「先转化、再删除」

命中禁写关键词**不等于**可以直接删。必须先还原这句话在约束读者什么：

1. 写出它隐含的前向约束
1. 检查该约束是否已被现有条款覆盖
1. 已覆盖 → 删除原句；未覆盖 → 改写成前向祈使句保留
实例：

| 原文（历史/快照） | 隐含约束 | 结论 |
| --- | --- | --- |
| 个人笔记「已迁至云文档平台」 | ①本仓库只收工程资产 ②文档权威在云文档平台 | 两条均已被现有条款覆盖 → 删 |
| 「当前活跃 AI 任务」表 | ①调度统一走定时任务平台、仓库不放提示词文件 ②邮件能力收敛进工具目录 | 转写为前向约束，表删除 |
| 「运行时配置目录由应用读取，勿改名」 | 只有「勿改名」是约束 | 删前半句 |
| 「曾清理 git 历史大文件，111M→25M」 | 禁止提交大二进制 | 上升为 Skill |

**移出不是删除，是搬到正确的位置。**

### 2.4 手段四：「先建承接点 → grep 验证 → 再删正文」

严格按此顺序，不可逆：

1. **先建承接点**：把内容写进目标文件
1. **grep 验证**：确认下游已完整承接
1. **再删正文**：验证通过才能删。绝不「先删了再说」
实际执行时，这一步拦下了真实缺口——**4 个承接点里有 2 个不合格**：

| 承接点 | 验证结果 |
| --- | --- |
| 工作流执行器 README | 完整覆盖 → 整节可删 |
| 插件宿主 README | 清单完整 → 枚举行可删 |
| 文档网关工具 README | **缺口**：多项约束未承接 → **先补后删** |
| 工具总表 README | **缺口**：6 个工具只登记了 3 个 → **先补后删** |

若跳过验证直接删，这些内容会永久丢失。

### 2.5 手段五：关键词扫描加入「章节号引用」

章节重排即失效，一律改为按名引用。实测命中 3 处，形如：

> 「知识文档权威源见**第四节**」→ 「见『跨域默认与硬性路由』」

这三处都是上一轮重排章节时自己埋下的定时炸弹。

### 2.6 手段六：语言一致性

规则文件正文、检查断言、所有者偏好语言，三者必须同语言。断言按文本包含判定、不跨语言匹配——不一致时全部断言零命中，**检查结果失去意义**。

排查要点：**全挂（****`proven: 0`****）是「基准与正文对不上」的信号；部分通过才是真正的规则缺陷。**

### 2.7 手段七：规则 vs Skill 的分界

判据是**触发是否自我 announce**：

- **Skill 靠检索命中**，前提是执行者意识到「我在做这类事」
- **规则进启动上下文**，用于执行者**压根没意识到需要**的约束
记忆同步纪律的典型失效方式恰恰是无意识——随手改了一处就收工，不会想到去找一个叫「记忆同步」的 Skill。所以拆成：**一条极短的触发规则 + 一个承接细节的 Skill，规则指向 Skill**。

反之 git 提交纪律的触发点是「我要提交了」，自我 announce 很清楚，且需让位于仓库本地 Skill——**只做 Skill，不进规则**，否则会以全局姿态压在每个仓库头上。

### 2.8 手段八：方向性错误走替换，不走自动迭代

自动迭代适合让**已经正确**的 Skill 变得更细，不适合修正**方向性错误**。连续四轮零采纳证明提建议这条路在该 Skill 上无效；最终由人工整体替换正文解决。

## 三、最终落定的规则

### 3.1 全局规则：长期知识改动三层同步

> **作用域**：单个 AI　**优先级**：80　**状态**：已生效

```
修改长期知识或规则时，若同一内容在多处有副本，必须按 项目规则文件 → 本地事实文件
→ 中央知识系统 的单向顺序更新，不得只改一处。三者冲突时以项目规则文件为准，本地事
实文件与中央知识系统均为下游副本，不具独立权威。写回中央知识系统时 upsert 同一稳定
id，绝不新建同义条目；为定位既有 id 优先复用本逻辑任务已有的检索结果，未检索过则计
入该任务的那一次检索。完整流程、副本内容约束与权威迁移后的指针清理见 Skill
memory-authority-sync。
```

**设计要点**：

- 优先级 80 低于既有的「每个逻辑任务只检索一次」规则（90），因为它只在**写路径**生效，不与检索节流争用
- 最后一句是**接缝焊接**：upsert 需要定位已有 id，而定位往往需要检索。不写清楚，执行者会在「该不该再检索一次」上卡住，或干脆新建同义记忆——正是硬禁令要防的事
- 正文只留触发条件与方向，完整流程下沉到 Skill

## 四、最终落定的三个 Skill

### 4.1 `maintain-agents-md`

创建、修改、精简任何给 AI 的规则文件时遵循的维护规范。

| 小节 | 内容 |
| --- | --- |
| 核心定位 | 规则文件是执行者的操作手册，不是项目简介、知识库或变更日志 |
| 三种职能 | 约束 / 默认 / 路由。**准入测试**：都不属于就不要写 |
| 两条硬约束 | 面向未来的祈使句；与实现无关 |
| 禁写清单 | 来源标记、历史事件、现状快照、描述性介绍 |
| 体量预算 | 整份 ≤200 行；单节 >10 行就移出（例外：根层注册表） |
| **层级归属** | 最小闭包原则 + 派生禁令（禁止双份权威） |
| **优先级与让位** | 就近者胜 + 全局须自带让位声明 + 覆盖必须有意 |
| **先转化、再删除** | 命中关键词不等于可删，先还原隐含约束 |
| 移出方法 | 先建承接点 → grep 验证 → 再删正文 |
| 定期体检 | 日期戳 / 完成动词 / 时间限定语 / **章节号引用** |
| 权限与能力 | 不登记清单，改为系统自省接口 |
| **语言一致性** | 正文、断言、偏好语言三者同语言 |

**加粗项为本轮新增。**

### 4.2 `git-commit-discipline`

向任何 git 仓库暂存、提交、推送前的入库纪律。

**关键设计——让位声明**：

```
本规则为跨仓库默认。所在仓库的规则文件或本地 skill 另有规定时，以仓库规定为准。
遇到下层与本规则矛盾，先判断是刻意差异还是下层陈旧未同步：陈旧应修下层，不默认
让下层胜出。
```

**关键设计——带出口的暂存规则**：

- 默认用精确路径 `git add path/to/file`，不用 `git add -A` / `git add .`
- **例外**：仓库已有明确产物忽略清单且 `.gitignore` 与之一致时可用 `git add .`，但提交前必须 `git status --short` 逐条核对
产物取舍的判定式：**「删掉它，能否用仓库内已有的东西重建？」能重建就不入库。**

体积防护的核心认知：大文件一旦进入历史，删除文件并不缩小仓库，清除需重写历史。**防线在提交前，不在事后。**

### 4.3 `memory-authority-sync`

长期知识在多处有副本时的同步纪律。

**核心原则**：

- 下游副本只存**结论 + 指回权威位置**，不复制正文。正文会漂移，复制即制造双份权威
- **按名引用，不按章节号引用**
**三层顺序**（原子操作，中途停下即埋雷）：

1. 规则层（行为真相）→ 项目规则文件
1. 事实层（持久上下文）→ 本地事实文件
1. 下游副本（可检索）→ 中央知识系统，upsert 同一稳定 id
**权威迁移后的扫描清单**：`.gitignore` 注释、README 反向引用、记忆条目中的路径与章节号、本地文档链接。

> 失效指针与双份权威同样有害：它会把执行者导向一个已经不存在的约束。

## 五、治理结果（工作区仓库实测）

### 5.1 体量与结构

| 阶段 | 行数 |
| --- | --- |
| 治理前 | 181 |
| 按层级归属下沉 | 105 |
| 按名引用 + 消除双份权威 | 107 |

净减 **41%**。注意：**瘦身不是目标**，181 行本就在预算内。真正的产出是分层正确。

### 5.2 下沉内容（按类型归并）

| 内容类型 | 去向 |
| --- | --- |
| 某一工具的调用约定、参数硬性规则、产物形态 | 该工具自己的 README（部分需先补写） |
| 某一工具的完整编排规范 | 该工具 README（已完整覆盖，整节直接删） |
| 端口号、插件名枚举、界面样式 | 各工具 README / 工具总表 |
| 跨仓库通用的工作方法 | 上升为 Skill，根文件只留指针 |

### 5.3 消除的双份权威与失效指针（5 处）

| 问题类型 | 处理 |
| --- | --- |
| 配置文件注释指向已重排的章节号 | 改为按名引用 |
| 本地事实文件指向已下沉的章节 | 改指承接它的 README |
| 下游 README 反向写「规则权威在根 AGENTS.md」 | 规则已下沉，反指构成环形 → 改为「本文件是唯一权威」 |
| 本地事实文件与规则文件的提交规则**互相对立** | 行为规则回落规则层，事实层只留本层该管的部分 |
| 知识条目指向已下沉的章节 | 改指承接它的 README |

第四条是**真冲突**，不是冗余：一边说「仅某个子目录自动推送、其余不自动提交」，一边说「全仓库完成即推送」。执行者读到哪份就照哪份做。

### 5.4 回归验证

| 扫描项 | 结果 |
| --- | --- |
| 日期戳 | 0 命中 |
| 完成动词 | 1 命中 → 是归档的判定条件，属约束正文，**通过准入测试** |
| 时间限定语 | 1 命中 → 是引号内的设问，属约束正文，**通过准入测试** |
| 章节号引用 | 0 命中 |
| 单节体量 | 非注册表节均 ≤9 行；两节超限属目录注册表，**命中明列例外** |

注意后两行：**关键词命中不等于违规**。扫描只负责提示，判定仍要回到三职能准入测试。

### 5.5 治理后的骨架

```
一、定位与核心原则         约束 + 默认
二、目录结构与根目录总账     路由（注册表，豁免体量限制）
三、各目录工作方式          约束（各目录的行为边界）
四、跨域默认与硬性路由       默认 + 路由（权威源、唯一入口、能力自省）
五、版本控制               约束（本仓库特有）+ 指向 git-commit-discipline
六、记忆与知识同步          约束（三层载体）+ 指向规则与 memory-authority-sync
七、工作区卫生             约束
```

每一节都通过「三职能准入 + 层级归属」双重检验。

## 六、可复用的结论

1. **规则文件的病灶通常不是太长，是分层错位。** 按行数体检会给出误导性的合格结论。
1. **历史信息不能删，要转化。** 「已迁至 X」的字面是历史，隐含的是路由约束与入库约束。直接删会连约束一起丢失。
1. **同一规则只能有一处权威。** 「本节是权威摘要」是最隐蔽的反模式——摘要必然漂移。
1. **移出前必须 grep 验证下游承接。** 实测 4 个承接点中有 2 个存在缺口，跳过验证就是永久丢失。
1. **全局规则必须自带让位声明。** 否则它会以全局姿态压在每个仓库头上。
1. **按名引用，不按章节号。** 章节号是自己给未来埋的定时炸弹。
1. **规则 vs Skill 的分界是「触发是否自我 announce」。** 执行者意识不到自己需要的约束，必须进启动上下文。
1. **正文、断言、偏好语言必须同语言。** 质检全挂是语言错配的信号，不是规则质量问题。
1. **自动迭代适合精修，不适合纠偏。** 方向性错误走替换流程。
1. **规范要能自证。** 用规范反查规范本身，是最便宜的质检——本次就查出它自己内嵌了 JSON 响应体。
