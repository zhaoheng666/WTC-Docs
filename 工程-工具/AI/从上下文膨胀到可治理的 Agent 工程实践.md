# 从上下文膨胀到可治理：项目 Agent 工程实践

> 核心结论：真正需要治理的不是上下文长度，而是权威来源、加载边界和执行职责。

## 分享摘要

随着 Claude Code、Codex 等 Agent 深入项目研发，我们遇到的问题逐渐从“Agent 不知道项目规则”变成了“Agent 知道得太多，却不一定在正确的时候使用正确的信息”。

项目规则、领域知识、Git 流程、长期任务和工具说明不断进入基础上下文。入口文件越来越长，模型每轮都要携带大量与当前任务无关的内容；与此同时，真正决定项目行为的规范仍可能因为触发条件不清而被漏读。为了提升可靠性而持续添加说明，反而带来了上下文膨胀、规则冲突、重复执行和交互耗时。

我们的解决方式不是继续压缩文字，而是建立一套可治理的 Agent 工程体系：明确谁是权威、什么内容常驻、何时按需读取、哪些工作交给 Agent 判断、哪些工作交给确定性程序执行。

最终，项目形成了“权威规范 → 常驻内核 → 按需路由 → 最小充分执行 → 确定性交付”的完整链路。

## 我们遇到的实际问题

### 1. 基础上下文越来越长，却没有变得更可靠

最初，为了让 Agent 理解项目，我们不断把术语、目录、构建命令、编码规则、Git 要求和专项说明加入入口文件。短期看，信息更完整；长期看，每个任务都要携带全部内容。

这产生了三个直接问题：

1. 无关上下文持续占用注意力和推理成本。
2. 规则、背景资料和临时项目状态混在一起，重要性难以区分。
3. Claude Code 使用 `CLAUDE.md`，Codex 使用 `AGENTS.md`，两份内容存在分叉风险。

入口文件越完整，不代表 Agent 越可靠。当所有信息都被放在最高优先级，真正关键的约束反而更难突出。

### 2. OpenSpec 已经是权威，但读取时机不清晰

项目已经使用 OpenSpec 定义正式行为和领域规则，但“OpenSpec 是权威来源”这一句话并不足以保证 Agent 会主动找到正确规范。

如果触发条件过窄，行为变更、缺陷诊断或代码审查可能漏读契约；如果要求所有任务都读取 OpenSpec，又会让普通编辑和机械 Git 操作承担不必要的检索成本。

问题的本质不是有没有规范，而是缺少从任务语义到规范的明确路由。

### 3. 长期项目状态污染了所有日常任务

DH 浏览器渐进式资源 Program 是一项庞杂、长线的项目工作。它包含大量目标、阶段、工件和验收信息，但这些内容只对参与该 Program 的任务有价值。

如果把长期项目写入常驻入口，任何无关任务都会被迫携带它。临时项目状态还会随着推进不断变化，使基础上下文快速过期。

### 4. 为了保证质量，执行链本身开始重复

当治理规则继续增加，Agent 容易把任务机械拆成多个阶段：实施后测试、测试后审查、提交时再次确认，甚至在 Git 操作中重新触发已经完成的收口。

类似的问题也出现在 SubAgent 和 Memory 调用上：如果每个局部动作都委派、每个相邻回合都重新检索，协调成本会超过实际收益。

治理原本用于降低风险，但缺少边界时，治理动作本身会成为新的耗时来源。

### 5. Git 提交是确定性工作，却消耗了大量模型交互

普通提交与推送包含范围确认、fetch、状态检查、暂存、提交、push、同步验证和结果整理。过去这些步骤由主 Agent 分多轮串行编排，每一步都需要读取输出并决定下一步。

提交完成后，结果中又同时出现摘要、原始日志、重复身份字段和远端信息。用户真正关心的是“提交了什么、是否推送成功、还有哪些变更未提交”，却要从大量低价值信息中寻找答案。

## 我们采用的治理方法

### 1. 从“一个大入口”改为“分层权威”

我们重新定义了不同内容的归属：

- OpenSpec 是项目行为、领域规则和正式契约的权威来源。
- `AGENTS.md` 是唯一常驻内核，只保存跨任务硬约束、通用路由和硬门禁。
- `CLAUDE.md` 通过符号链接复用 `AGENTS.md`，不再维护第二份副本。
- Skill 保存特定任务的完整工作流。
- 详细规则和项目参考保存在专项文档中，命中任务时再读取。
- Change 和 Program 保存当前工作状态，只服务真正属于它们的任务。

这次调整的关键不是把内容从一个文件搬到另一个文件，而是为每类信息建立清晰的生命周期和加载边界。

### 2. 用任务语义触发 OpenSpec 有界检索

我们把 OpenSpec 的触发条件定义为：当任务需要确定、解释、修改或验证项目行为、领域规则或正式契约时，先根据任务语义和受影响路径检索正式规范。

同时增加三项约束：

1. 只读取命中的规范，不在未命中时扩展为全量扫描。
2. 同一任务复用已经读取的规范，范围不变就不重复检索。
3. 只有任务实际属于某个 Change 或 Program 时，才读取其在途工件。

这让行为变更、缺陷诊断、代码审查和验收获得足够覆盖，也避免无关任务被规范检索拖慢。

### 3. 用“最小充分证明”替代机械阶段

Agent 不再为了遵循流程而创建固定数量的阶段，而是只建立真实依赖所需的工作步骤。

测试、审查和验收范围由风险和证据决定：局部验证足以证明正确时不做无依据扩张；共享 Runtime、资源身份、生成契约和发布切换等高风险范围，仍保留独立 verifier 和领域硬门禁。

最后一次实质修改完成后统一收口，Git 提交只消费仍然有效的收口结论，不重新启动广泛测试或审查。

### 4. 把判断工作留给 Agent，把重复工作交给程序

SubAgent 只在独立复核、真实并行、专门知识或上下文隔离具有明确收益时使用。可重复、局部且结果可判定的操作，不再通过新增 Agent 层级解决。

Git 提交就是典型案例。我们将普通流程编写为确定性辅助程序，并收敛为两个批次：

1. `prepare`：完成提交范围预检、远端同步和状态绑定。
2. `deliver`：完成精确暂存、提交、推送和同步验证。

程序负责校验仓库、分支、HEAD、upstream 和文件范围，发现状态漂移立即停止。普通快速路径不执行 force push；如需改写远端历史，必须脱离该路径并另行取得用户明确授权。

主 Agent 只需要提供提交范围和提交说明，不再逐条解释 Git 输出并手工编排每个局部步骤。

### 5. 将系统级能力与项目规则分开

Nowledge Memory 是宿主提供的跨工具能力，不属于 WorldTourCasino 的项目行为。我们没有把它写进 `AGENTS.md`，而是在系统级建立“一次逻辑任务一次有界检索、相邻回合复用”的路由。

这样既能保留跨会话决策，又不会让每个项目任务都重复调用 Memory，也避免项目规则与具体 Agent 宿主绑定。

## 最终取得的效果

### 上下文更一致

- Claude Code 与 Codex 使用同一个基础上下文来源。
- `CLAUDE.md` 与 `AGENTS.md` 不再发生内容漂移。
- 常驻入口只保留真正跨任务的不变量。
- 长期 Program 和详细专项知识按需加载，不再污染普通任务。

### 规范读取更准确

- 涉及行为和契约的任务会主动检索 OpenSpec。
- 普通编辑和机械 Git 操作不会触发全量规范读取。
- 同一任务复用已获取的规范和 Memory 结果，减少重复路由。

### 执行链更短

- 普通 Git 编排由四段收敛为两段。
- fetch 和 push 各执行一次。
- 同类任务样本从 81.101 秒降至 65.708 秒，减少约 19%。

这组数据反映的是串行编排减少后的样本效果。整轮 Agent 耗时还会受到模型推理、上下文压缩和网络波动影响，因此我们不把界面总耗时直接等同于程序性能。

### 安全门禁没有因提速而削弱

- Git 辅助程序通过九类行为场景验证，覆盖正常提交、无关脏文件、状态漂移和异常停止。
- 提交范围与前置状态绑定，降低误提交风险。
- 普通快速路径不执行 force push；改写远端历史必须另行取得用户明确授权。
- OpenSpec strict validation 19/19 通过，本次收口时没有 active Change。

### 交付结果更容易阅读

提交结果只展示用户真正需要的信息：提交标题、交付状态、分支、同步状态、完整 Hash、提交者、提交说明、文件统计和未提交边界。

原始 `fullLog`、重复身份、时间和远端字段不再固化到成功输出中。信息减少了，但决策价值更高。

## 这次实践带来的认识

### 1. 上下文治理的第一步是确定权威，而不是删字

如果多份文件都可以定义同一件事，再短的上下文也会冲突。先明确唯一事实来源，再决定哪些内容常驻、哪些内容按需加载。

### 2. 按需加载必须有可执行的语义触发条件

“需要时读取”不是规则。有效的路由必须说明什么任务需要读取、到哪里检索、读取多大范围，以及何时可以复用已有结果。

### 3. Agent 擅长判断，程序擅长重复

需求理解、风险分析和范围判断适合 Agent；状态校验、精确暂存和固定格式解析更适合确定性程序。让 Agent 反复执行可编程步骤，只会增加交互成本和不确定性。

### 4. 更多治理动作不等于更安全

重复审查、重复检索和机械委派不会自动提高质量。治理应围绕风险建立最小充分证明，并在高风险位置保留真正独立的验证。

### 5. 效率评估必须区分不同耗时层级

程序执行时间、网络时间、模型推理时间和上下文压缩时间不能混为一谈。只有分层测量，才能判断优化是否真正有效。

## 收束

这次实践最终解决的，不只是一个 `AGENTS.md` 或 `CLAUDE.md` 太长的问题，而是建立了项目与 Agent 之间更清晰的协作契约：

- 项目用 OpenSpec 说明什么是正确的。
- 常驻上下文告诉 Agent 哪些边界永远不能越过。
- 路由和 Skill 决定当前任务需要加载什么。
- Agent 负责理解、判断和处理例外。
- 确定性程序负责重复、可验证的操作。

当这些职责被分开以后，上下文更少只是自然结果；更重要的成果是，Agent 的行为变得更一致、更可解释，也更容易持续维护。
