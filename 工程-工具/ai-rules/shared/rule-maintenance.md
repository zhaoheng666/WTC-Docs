# 项目规则与基础上下文维护

本文档定义 WorldTourCasino 的基础上下文分层与规则放置方式。目标是
让 Agent 启动时拿到最小但足够的共享内核，在任务匹配后再加载权威规范、
Skill 和专项参考。

## 分层模型

| 层级 | 作用 | 位置 | 维护原则 |
| --- | --- | --- | --- |
| 权威语义 | 定义可验收行为、不变量和领域门禁 | `openspec/specs/`、当前 Change/Program | 通过官方 OpenSpec 流程修改 |
| 共享常驻内核 | 保留跨任务硬约束、通用入口路由和硬门禁 | `AGENTS.md` | 稳定、简短、不展开专项流程 |
| 宿主文件名兼容 | 让 Claude Code 与 Codex 读取同一实体 | `CLAUDE.md -> AGENTS.md` | 使用符号链接，只编辑 `AGENTS.md` |
| 任务流程 | 定义边界清晰、可执行的工作流 | `.claude/skills/` | 按 Skill 触发；官方生成 Skill 不手改 |
| 专项参考 | 保存详细规范、示例和背景知识 | `docs/工程-工具/ai-rules/` | 只在任务匹配时加载 |

`AGENTS.md` 是唯一共享入口：只读取它的 Agent 必须能发现所有必需项目约束和任务路由。
`CLAUDE.md` 是指向 `AGENTS.md` 的符号链接，不是第二份共享规则副本。两个入口因此逐字节一致，
也不存在独有的项目地图、命令、约束或路由。
`AGENTS.md` 也不应变成项目百科；可从当前代码、仓库状态或权威工件按需获取的信息，
应由 `AGENTS.md` 路由到专项参考。
长期 Program 或其他大型项目工作即使周期长、范围广、门禁多，其恢复顺序、状态和领域收口协议
仍属于该 Program 自身，不得因为复杂或长线而固化到 `AGENTS.md`。

## 放置决策

| 问题 | 放置位置 |
| --- | --- |
| 需要成为可验收的项目行为或领域契约？ | 用官方 OpenSpec 流程修改 `openspec/specs/` |
| 是否跨绝大多数任务、容易误触且恢复代价高？ | 在 `AGENTS.md` 保留一条简短不变量，详情链接权威来源 |
| 是否只是 Claude Code 对入口文件名的兼容需求？ | 保持 `CLAUDE.md -> AGENTS.md` 符号链接，不新增内容 |
| 是否有明确起止、触发条件和执行步骤？ | 项目 Skill |
| 是否为可延迟加载的详细规范或参考？ | `docs/工程-工具/ai-rules/` 中的专项文档 |

一条规则可以有“常驻摘要 + 权威详情”，但不应在多个入口复制整段文案。
`CLAUDE.md` 不单独编辑；对链接路径的修改等价于修改 `AGENTS.md`。

## 维护流程

1. 先搜索 `AGENTS.md`、`CLAUDE.md`、相关 Skill、专项规则和 OpenSpec，确认是新规则、语义修订还是去重。
2. 语义变更先通过官方 OpenSpec proposal/update 流程修改权威契约；仅结构化、去重或修正路由时，保持现有语义不变。
3. 将跨任务硬约束的最短表达和必需任务路由放入 `AGENTS.md`；保持 `CLAUDE.md` 为指向它的符号链接；项目地图和命令放入按需参考文档。
4. 复用既有 Skill 和文档；无相关资源时才新建。项目自定义 Skill 只在 `.claude/skills/` 维护。
5. 扫描重复段落、失效入口、本机绝对路径和与当前 OpenSpec/Skill 冲突的历史文案。
6. 修改 Agent 规则后运行 `npm run check:openspec`；修改其他文档时执行受影响的最小充分检查。
7. 在最后一次实质修改后使用 `code-review` Skill 收口。

## 质量检查

- `AGENTS.md` 是否仍只包含跨任务内核、通用工作流路由和硬门禁？
- 是否将某个长期 Program 的恢复顺序、状态或领域收口协议误放入了常驻上下文？
- 只读取 `AGENTS.md` 的 Agent 是否能发现所有必需项目约束和任务路由？
- `CLAUDE.md` 是否仍是目标为 `AGENTS.md` 的符号链接，而非普通文件或独立副本？
- 行为性要求是否能追溯到 OpenSpec 或其他明确权威来源？
- 同一详细规则是否只在一处完整定义，其他位置只做摘要或路由？
- 是否删除了过时命令、人工二次确认、旧 OpenSpec 入口等冲突说法？
- 所有仓库路径是否可移植，所有链接是否符合所在子项目规则？
