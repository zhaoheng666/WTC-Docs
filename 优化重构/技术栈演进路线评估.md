# 技术栈演进路线评估

> **创建日期**: 2026-08-03
> **状态**: 讨论稿（供团队决策参考）
> **背景**: 项目在线运行多年，代码与资源持续堆积，技术栈（Cocos2d-html5 + CocosBuilder + ES5）已落后于当下；Unity 迁移方案（见 [unity-migration](http://localhost:5173/WTC-Docs/unity-migration/00-index)）经实施尝试后确认成本过高，本文评估其余可选路线。

---

## 一、问题拆解：迁移是手段，不是目标

"转引擎"把两个不同的问题捆绑成了一个昂贵的解：

- **臃肿**（代码/资源堆积）——迁移解决不了，内容搬到新引擎依然臃肿
- **落后**（DX/性能/人才/生态）——未必需要迁移，项目自持引擎 fork，有点状升级的权力

| 痛点 | 症状 | 是否需要换引擎 |
| --- | --- | --- |
| 代码臃肿 | 133 万行 ES5（6,463 个 JS 文件），死代码/重复实现堆积 | ❌ 瘦身即可 |
| 资源臃肿 | 4 风格 × 500-600MB，长尾机台占大头 | ❌ 退役 + 压缩即可 |
| 开发体验落后 | ES5 手写、无类型、Browserify | ❌ 构建链现代化即可 |
| 性能瓶颈 | 加载/内存/渲染 | 🟡 多数可点状修（ResourceManV2、延迟 GPU 上传等已在做） |
| 人才/生态 | 新人不愿写 ES5，社区已死 | 🟡 TS 层可缓解，长期确实是引擎问题 |
| 平台风险 | 引擎无人维护、依赖废弃 API | 🟡 唯一真正指向迁移的理由；自持 fork（v3.13-lite-wtc），风险可控 |

**六个痛点里最多两个真正指向换引擎，且都不紧急。**

### 迁移成本高的根因

**内容（300+ 机台）与引擎 API 深度耦合，迁移成本 = O(内容数量)。**

Unity 方案用 4 层兼容架构（L1 Cocos 兼容层 → L4 关卡迁移）试图机械化这个 O(n)，但每个机台的翻译 + 验证成本乘以数量后依然不可行。换目标引擎（如 Cocos Creator）不改变这个成本函数——出路是**改变成本函数本身**（见方案 B/C）。

## 三、已评估的迁移路线

### 3.1 Unity 6（已尝试，成本过高）

完整方案见 [unity-migration 系列文档](http://localhost:5173/WTC-Docs/unity-migration/00-index)（4 层架构：L1 Cocos 兼容层 / L2 Slot 框架层 / L3 适配层 / L4 关卡迁移）。

**结论**：兼容层设计合理，但 O(机台数) 的翻译 + 逐台回归验证成本在实施中被确认不可行。

### 3.2 Cocos Creator 3.x（评估结论：与 Unity 无本质区别）

分层损耗评估：

| 层 | 迁移通道 | 损耗评估 |
| --- | --- | --- |
| 纹理图集（plist）/音频/字体 | Creator 原生支持 cocos2d 格式 plist | 🟢 近无损，可全自动 |
| 配置数据（ActivityConfig 等）/服务器协议 | 纯数据，引擎无关 | 🟢 无损 |
| Slot 数学模型/服务器交互逻辑 | 取决于与显示层解耦程度 | 🟡 可复用，需从 cc.Class 剥离 |
| CCB/CCBI 场景（1.8 万+/风格） | 无官方通道，社区工具陈旧且仅覆盖已 EOL 的 Creator 2.x | 🟡 需自研转换器；时间线动画/自定义类绑定/rootVar 语义需映射 + 人工校对 |
| 业务代码（133 万行） | 无自动通道 | 🔴 `cc.Class.extend` 继承式 → 组件式范式重写，非语法转换 |
| 引擎定制（lite-wtc fork） | — | 🔴 每个定制点需重新实现 |
| ResourceManV2 / 热更 / 版本体系 | Creator Asset Bundle | 🟡 整体重设计 |

**三个决策级约束**：

1. Creator 2.x 已 EOL，只能选 3.x（TypeScript + 全新渲染管线），与 ES5 代码库距离进一步拉大
2. 双轨维护是最大隐性成本：产品在线运营、赛季活动不停更，迁移期团队需双份产出，以此体量估算以"年"计
3. 与 Unity 路线可共享的资产相同（CCB 解析工具链、资源转换、逻辑解耦），并行开两条迁移线没有意义

**一句话结论**：资源无损、逻辑高复用、场景半自动、代码全重写——"无损"若指不重写业务代码，则 Creator 与 Unity 没有本质区别。

## 四、替代方案矩阵

### 方案 A：原地现代化（成本最低，立即可行）

不换引擎，换**写代码的方式**：

```
新构建链：TypeScript / ES6+ 源码 ──(esbuild, target: es5)──▶ ES5 产物
           │
           └─ 为 cc.* API 手写 .d.ts 声明（只覆盖常用面，增量补齐）
```

- 新代码获得类型检查、现代语法、IDE 补全；产物仍是 ES5，与存量代码零冲突
- 存量 133 万行**不动**——在跑、在产生营收的代码，重写没有商业回报
- 配套瘦身：机台退役制度（按营收 Pareto 砍长尾）、死代码清理、纹理压缩（WebP/ASTC）
- 现有 AI 工具链（skills、AI 关卡蓝图）在此方案下全部保值

### 方案 B：数据驱动内容管线（战略核心）

真正改变成本函数的一步。Slots 机台高度模式化：**转轴配置 + 赔付表 + 图集 + 时间线动画 + 少量特殊玩法**。

```
现状：每个机台 = CCB 场景 + 手写 controller 代码   → 与引擎深度耦合
目标：每个机台 = 声明式数据包（蓝图 JSON + 图集 + 动画描述） + 通用播放器
                    │
                    └─ 引擎从"开发平台"降级为"播放器实现"
```

- 新机台产出不再写引擎代码 → **臃肿停止增长**（治本）
- [AI关卡产出蓝图模板](http://localhost:5173/WTC-Docs/关卡/AI关卡产出蓝图模板) 与 AI 关卡研发流程说明这条路已在走——从"AI 辅助产出代码"升级为"AI 产出纯数据"是方向上的半步之遥
- 特殊玩法用受限的脚本扩展点承接，控制数据格式的表达力边界

### 方案 C：绞杀者模式（长期，可选终局）

有了方案 B 的数据格式，"迁移"的语义就变了：

```
迁移 300+ 机台（O(n) 内容成本，Unity 路线死在这里）
        ↓ 变成
用新技术栈实现一个"蓝图播放器"（O(1) 播放器成本）
   ├─ 新机台：直接跑在新播放器上
   ├─ 高营收老机台：按蓝图格式重制（只做 Top 20%）
   └─ 长尾老机台：留在老引擎或退役，自然消亡
```

播放器技术选型此时才有意义，且选项比 Unity/Creator 更轻：**PixiJS + Spine** 类轻量渲染栈对 2D Slots 是行业常规选择——需要的是精灵 + 图集 + 时间线动画 + UI，不是全功能游戏引擎。

### 方案 D：AI 辅助迁移复评（谨慎的补充项）

若 Unity 成本结论形成于 agentic 工具成熟之前，"CCB 解析 + controller 语义翻译"的人工成本估算可能已过时。但 AI 降低的是**翻译成本**，**验证成本**（逐台回归）纹丝不动——只能作为方案 C 中"Top 20% 重制"的加速器，救不活全量迁移。

## 五、推荐路径

| 阶段 | 动作 | 治什么 |
| --- | --- | --- |
| **近期（1-2 月）** | 方案 A：TS 构建链 + 机台退役制度 + 资源压缩 | 落后的 DX、资源臃肿 |
| **中期（本年度）** | 方案 B：定义机台蓝图格式，新机台全部数据驱动（沿 AI 蓝图路线深化） | 臃肿停止增长、内容与引擎解耦 |
| **长期（明年起，可选）** | 方案 C：新栈实现蓝图播放器，Top 机台重制，长尾自然退役 | 技术栈换代，成本 O(播放器) 而非 O(机台) |

**核心论点**：不要再问"迁到哪里便宜"——**当机台变成数据，引擎就变成了播放器，播放器是可以随时换的**。Unity 路线的受挫恰恰证明：贵的从来不是引擎，是被引擎绑架的 300 个机台。
