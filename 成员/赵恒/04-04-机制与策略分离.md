# 04 机制与策略分离

> 源自飞书文档 · 最后同步：2026-10-30

**一句话**：机制回答「怎么做」，稳定、通用；策略回答「做什么 / 何时做」，随业务变化。策略以带 schema 的数据或策略对象注入机制，机制代码里不得出现活动 ID、渠道、环境的判断。

> 层级：L2 切分 ｜ 对应痛点：需求频繁变更导致返工；配置或数值出错、线上事故；多项目或多款游戏复用困难 ｜ 来源：原文《机制与策略分离》 + 本文扩展

## 为什么需要它

机台之间的差异大多是「规则不同」而非「能力不同」：赔付、卷轴带、活动触发、重试参数。规则若写进代码，每次调整都要改代码、发版、回归，需求一变就返工；机制若随机台复制，则无法复用。把变的部分交给数据，稳定的部分沉淀为机制，需求变更才会变成改数据，而不是改代码。

## 核心主张

- 判别问句：「这条规则下个月由谁来改？」策划或运营改的是策略，程序员改的是机制。
- 策略以数据优先，其次才是策略对象；两者都经类型化接口注入，并通过 schema 校验（见 05）。
- 机制里出现活动 ID、渠道、环境的 `if`，就是策略泄漏：必须提取成配置注入或策略回调。
- 机制只抽象稳定且高频复用的能力；过度泛化的「空洞机制」参数繁多、难读且慢。
- 数学模型是「策略数据加结算机制」：数据可配，结算算法是机制，数据一变就要模拟回归（见 05、09）。
## 怎么做

1. 清点一个机台里的全部规则，逐条问判别问句，归入下表两侧：
| 类别 | Slots 里的典型内容 | 谁来改 |
| --- | --- | --- |
| 机制 | 转轴驱动、赢线计算引擎、动画队列、资源加载队列 | 程序 |
| 策略 | 赔付表、卷轴带、特性触发规则、活动规则、重试与限流参数 | 策划、运营，或服务端配置 |

1. 由机制定义策略接口，接口小而类型化：只暴露机制需要外部决定的事（要不要重试、等多久；这条线怎么赔）。
1. 数据优先：能用一份数据表达的，不写成代码。只有数据表达不了（如多条件组合的触发）才用策略对象或回调，且仍由配置选择，不在机制内写分支。
1. 装配点收口：在一个地方，按机台配置把机制与策略绑定。机制与组件代码里不出现机台名、活动 ID、渠道或环境判断。
1. 抽机制按 R2：第二款机台出现同样的机制需求才抽接口，第一次先写在机台里。不预先发明通用工作流 DSL，也不要把具体流程写进内核（见 03）。
1. 数学模型：赔付表、卷轴带是策略数据，赢线计算与结算是机制。若产品涉及真实资金或受监管，权威结算在服务端（见 09），两端使用同一份带版本号的数据（见 05）。
```typescript
// 策略接口：只回答「要不要重试、等多久」
interface RetryPolicy {
  shouldRetry(attempt: number, err: unknown): boolean;
  delayMs(attempt: number): number;
}
// 机制：怎么重试。不出现次数、间隔、环境判断（sleep 为通用延时函数）
async function withRetry<T>(fn: () => Promise<T>, p: RetryPolicy): Promise<T> {
  for (let attempt = 1; ; attempt++) {
    try { return await fn(); }
    catch (err) {
      if (!p.shouldRetry(attempt, err)) throw err;
      await sleep(p.delayMs(attempt));
    }
  }
}
// 策略：由配置选择，数值为示例，须按项目实测设定
const assetLoad: RetryPolicy = { shouldRetry: (n) => n < 3, delayMs: (n) => 500 * 2 ** (n - 1) };
const failFast: RetryPolicy = { shouldRetry: () => false, delayMs: () => 0 };
await withRetry(() => loadMachineAssets(id), assetLoad);
```

## 在 Slots / Cocos 项目里的落地

| 场景 | 做法 | 反例 |
| --- | --- | --- |
| 转轴与卷轴带 | 转轴驱动是机制（怎么转、怎么停）；卷轴带与停轴权重是策略数据，随机台配置 | 每款机台复制一份转轴脚本，卷轴带写成代码里的数组常量 |
| 赢线与赔付 | 计算引擎读取赔付表与线型数据，改赔付只改数据 | 赔付写成 if-else 链，改一次赔付要改代码并发版 |
| 活动与特性触发 | 触发条件、权重、时段是配置，机制只负责按规则触发并播放 | 机制里写 `if (activityId === ...)` |
| 动画队列与资源加载队列 | 队列与重试是机制；重试次数、并发数、限流参数是策略 | 把 3 次重试、1 秒间隔写死；渠道不同就复制一份 |
| 机台差异的注入 | 机台组件把策略数据注入机制（见 03） | 平台代码按机台 ID 分支 |

## 评审清单

| 评审类型 | 检查问句 | 不通过信号 |
| --- | --- | --- |
| 设计评审 | 每条规则是否回答了「下个月由谁改」并归入机制或策略？ | 说不清；策划要改的写在代码里，或程序要改的塞进配置 |
| 设计评审 | 机制是否定义了小而类型化的策略接口，策略数据是否有 schema 与校验？ | 策略以无类型 JSON 或魔法字符串传入 |
| 设计评审 | 抽取该机制是否有第二个真实使用方（R2、R5）？ | 为想象中的通用性设计，参数层层泛化 |
| 设计评审 | 是否避免了通用工作流 DSL 与「万物可配」？ | 配置里出现条件嵌套、循环、脚本片段，变成隐形 DSL |
| 代码评审 | 机制代码里有没有活动 ID、渠道、环境、机台名的分支？ | `if (env === 'PROD')`、`if (activityId ...)` |
| 代码评审 | 重试次数、间隔、阈值是否经注入而非硬编码？ | 机制内部的魔法数字 |
| 代码评审 | 新增一种赔付或活动，是否只改数据或策略，不改机制？ | 加规则要动机制并全量回归 |
| 代码评审 | 对结算类请求套用重试策略时，是否带幂等号（见 09）？ | 未带幂等号的结算请求被自动重试 |

## 误用与反模式

- 策略泄漏进机制：机制里出现活动 ID、渠道、环境的 `if`。
- 机制空洞：为通用而泛化，参数过多、层层代理，可读性与性能双损。
- 提前发明通用工作流 DSL：把具体流程变成配置语言，调试困难，成为隐形代码。
- 把具体流程写进内核：内核硬编码某个机台的 Spin 流程，换机台就要改内核（见 03）。
- 万物可配：把本应是代码的机制也配置化，配置错误成为事故来源（见 05）。
## 取舍与边界

- 不用：只出现一次、几乎不会变的规则，直接写在代码里（R2、R5）；原型期不必抽策略接口。
- 与 03：内核只留机制，策略在组件或配置里。与 05：策略数据化后必须有配置治理，分离的收益靠 05 兑现。
- 与 07：策略接口是「做什么」的决定，端口是对外部依赖的抽象，两者不要混用术语。
- 与 09：策略数据决定结果，涉及资金时须服务端权威并做模拟回归。
- 与 R1：配置化会扩大线上事故面；高危数据（金额、概率、赔付）宁可保守，按 05 分级治理，风险优先于灵活性。
- 与 01：变更先分类，改策略即改配置，是最便宜的变更路径。
## 可执行的检查

| 检查项 | 执行位置 | 判定标准 |
| --- | --- | --- |
| 机制纯度扫描 | 提交 / CI | 机制目录中不出现活动 ID、渠道名、环境名的字面量或比较，命中数为 0 |
| 策略数据校验 | CI | 每份策略数据通过 schema 与范围校验（见 05），未通过阻断合并 |
| 机制目录改动标注 | CI | 新增赔付或活动的 PR，机制目录 diff 应为空；有改动须标为「机制变更」并走机制评审 |
| 模拟回归 | CI / 发布 | 策略数据变更后批量模拟，命中率与回报率在预期容差内，容差按项目设定（见 05、09） |
| 策略版本留痕 | 线上 | 日志与埋点带策略数据版本号，事故时能还原当时生效的数据 |
