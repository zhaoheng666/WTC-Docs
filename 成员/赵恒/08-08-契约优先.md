# 08 契约优先

> 源自飞书文档 · 最后同步：2026-10-30

**一句话**：跨团队、跨进程、跨版本的接口，先写下并冻结一份可机器校验的契约，再各自实现（见规则 R3）；契约不只是字段，还要写清输入输出、作用范围、资源归属、取消与超时、失败语义、幂等与版本兼容，变更走 PR 与双方会签，由 CI 拦截破坏性变更。

> 层级：L3 接缝 ｜ 对应痛点：策划、美术、程序、服务端联调扯皮；需求频繁变更导致返工；配置或数值出错、线上事故 ｜ 来源：原文《契约优先（Contract-First Design）》

## 为什么需要它

联调扯皮的根源常是约定停留在口头与聊天记录：字段含义、错误码、超时后该不该重发，各方理解不同，一方改动另一方上线后才发现。先写契约，各方就能依据同一份文本并行开发，并让「谁改了什么、谁同意了」有据可查。

## 核心主张

- 契约先于实现：在写任何一行实现之前，先定义并冻结跨团队、跨端通用的契约文件。
- 契约必须可机器校验：能生成类型与 mock、能做破坏检测，只存在于文档里的说明不算契约。
- 契约不止字段：没有生命周期、错误与幂等语义的接口，联调照样扯皮。
- 冻结有时机（规则 R3）：原型期、单人单模块内不冻结；一旦跨团队、跨进程、跨版本，立刻冻结。
- 变更有流程：契约进版本库，改动走 PR，双方会签，不兼容改动让新旧版本并存一段迁移期。
## 怎么做

1. 判断是否该冻结：这个接口是否跨团队、跨进程或跨版本？是则起草契约；否则先用原型演进，不开契约评审。
1. 选载体：按团队技术栈选 OpenAPI、Protobuf、JSON Schema 等可校验格式；原文还列出 GraphQL Schema。载体只是形式，语义要求相同。
1. 写语义而非只写字段：每个接口写明输入输出、作用范围、资源归属、取消与超时、失败语义、幂等、兼容策略。
1. 契约进版本库，独立目录或仓库，改动必须提 PR，由使用双方会签。
1. 由契约生成类型、校验器与 mock，客户端、服务端、策划工具各自生成，不再手写重复定义。
1. CI 做破坏性变更检测：删字段、改类型、收紧枚举、改必填一律拦截；确需不兼容时发新版本，新旧并存并写明迁移期。
1. 用 mock 与录制回放让各方并行开发；联调时用同一份契约验证两端。
```yaml
# 示例：Spin 请求的契约片段（载体可为 OpenAPI、Protobuf、JSON Schema，按团队技术栈）
contract: SpinRequest
version: 2.1.0                # 示例；删字段、改类型、收紧枚举视为破坏性变更
request:
  requestId: { type: string, required: true }   # 幂等号：重复请求只结算一次
  betLevel:  { type: int, min: 1 }
response:
  roundId: { type: string }
  status:  { type: enum, values: [settled, pending, rejected] }
unknown_enum: "客户端遇到未知枚举值时按 pending 处理并上报"   # 示例规则
errors:
  - { code: DUPLICATE_REQUEST, retry: false, action: "返回原结果" }
  - { code: INSUFFICIENT_BALANCE, retry: false }
  - { code: TIMEOUT_UNKNOWN, retry: false, action: "先按 requestId 查询，禁止直接重发" }
semantics:
  timeout_ms: "示例值，按项目实测设定"
  idempotent: true
  compat: "新增可选字段允许；删除或改类型须新版本并存"
```

## 在 Slots / Cocos 项目里的落地

| 场景 | 做法 | 反例 |
| --- | --- | --- |
| 客户端与服务端协议（Spin 请求与响应） | 契约含幂等号、错误码、超时与失败语义，生成类型与 mock | 靠聊天记录约定字段，错误码「以服务端代码为准」 |
| 配置表 schema（见 05） | schema 随版本发布，导出器与校验器共用同一份 | 策划改了表头，程序在代码里另写一份解析 |
| 埋点事件 schema | 事件名、必填字段、取值范围入契约库，CI 校验上报样例 | 埋点口头约定，数据侧发现缺字段时已上线 |
| 资源规范（命名、目录、尺寸、图集） | 写成机器可校验的规则文件（见 13） | 靠美术自觉，进包后才发现超标 |
| 组件扩展接口（见 03） | 声明生命周期、资源归属、清理义务与版本范围 | 接口只有函数名，加载后由谁释放无人知晓 |

## 评审清单

| 评审类型 | 检查问句 | 不通过信号 |
| --- | --- | --- |
| 设计评审 | 这份接口是否跨团队、跨进程或跨版本，是否已冻结并有版本号（规则 R3）？ | 已经跨团队仍然「边做边改」 |
| 设计评审 | 契约是否写明输入输出、作用范围、资源归属、取消与超时、失败语义、幂等、兼容策略？ | 只有字段名或函数名 |
| 设计评审 | 变更是否有双方会签与新旧并存的迁移期安排？ | 服务端改完「通知一下」 |
| 设计评审 | 契约能否被机器校验并生成类型或 mock？ | 契约只存在于文档页面 |
| 设计评审 | 单人单模块或原型期的接口是否被过早冻结？ | 每改一个字段都要开评审会 |
| 代码评审 | 实现是否使用契约生成物，而非手写重复定义？ | 同一结构在客户端、服务端、工具里各写一份 |
| 代码评审 | 改动是否触及契约文件，是否带变更说明与破坏检测结果？ | 业务代码里悄悄多了字段 |
| 代码评审 | 遇到未知枚举值、多余字段时，是否有明确处理？ | 直接崩溃，或静默吞掉 |
| 代码评审 | 错误码、超时、重复请求分支是否有测试？ | 只测成功路径 |

## 误用与反模式

- 契约只有字段清单：缺生命周期、错误与幂等语义，是根文档对照表点名的误用。
- 把文档当契约：说明页不可校验，很快过期，等于没有契约。
- 过早冻结（契约僵化）：原型期每改一个字段都走会签，拖垮探索速度。
- 代码优先当契约用：服务端改实现即改契约，客户端被动适配，回到原文批评的代码优先困境。
- 只检字段不检语义：字段没删但含义变了（比如金额单位由分改为元），破坏检测查不出来，须在变更单写明并由契约测试覆盖。
## 取舍与边界

- 不用或延后：单人单模块内部接口、尚在探索的原型；此时过早冻结的成本高于收益。冻结不等于永不修改，而是修改有流程。
- 与 07：端口只是形状，契约还含语义；与 05：配置 schema 是契约的一种；与 09：幂等号与回合状态是协议语义的核心；与 11：破坏检测是适应度函数，交给 CI（规则 R6）。
- 与 10：原型阶段先演进，满足规则 R3 的条件再冻结。
- 裁决：规则 R3 决定何时冻结；涉及结算权威边界、账务数据结构的字段语义属于单向门（见 01），冻结要更早、会签要更严（规则 R1）。紧急线上修复可走加急通道，但仍要补 PR 与会签记录。
## 可执行的检查

| 检查项 | 执行位置 | 判定标准 |
| --- | --- | --- |
| 契约破坏性变更检测：删字段、改类型、收紧枚举、改必填 | 提交 / CI | 发现破坏性变更且未发新版本则失败 |
| 生成物一致性：类型与 mock 与契约同版本 | CI | 契约已变而生成物未更新则失败 |
| 契约样例校验：请求与响应样例对照 schema | CI | 任一样例不符合 schema 则失败 |
| 契约测试：服务端用同一份契约，客户端用 mock | CI / 联调前 | 两端均通过才允许联调 |
| 变更单审计：契约文件变更须关联双方会签 | PR | 缺少任一方会签则阻止合入 |
| 未知字段、未知枚举值、契约外错误码计数 | 线上 | 出现即告警（阈值按项目设定） |

## 来源与扩展

- 来自原文《契约优先（Contract-First Design）》：先契约后实现并冻结；代码优先与契约优先的对比；契约载体（OpenAPI、Protobuf、GraphQL Schema）与工具链思路（生成类型、mock、破坏检测）；契约进 Git 并走 PR 评审；CI 做破坏性变更检测；避免契约僵化，原型期可不冻结，一旦跨团队立刻冻结。原文的 YAML 示例排版错乱、且以订单 REST 接口为例，本卡未照搬，改为 Spin 协议示例。
- 来自根文档对照表：先定义输入输出、作用范围、资源归属、取消与失败语义，再写实现；误用是接口只有函数名、没有生命周期与错误约束。
- 本文扩展：Slots 契约清单（协议、配置 schema、资源规范、埋点、组件接口）、幂等与超时语义、双方会签、录制回放、新旧版本并存。
- 需按实际核对：具体工具与版本（如生成类型、mock、破坏检测工具）按团队技术栈与所用版本核对；协议载体选型（Protobuf 或 JSON 等）按团队实际；超时、重试数值按项目实测；若涉及真实资金或受监管，账务相关字段的留痕与审计要求按所在辖区核对。
