# 14 团队边界与知识沉淀

> 源自飞书文档 · 最后同步：2026-10-30

**一句话**：先定系统边界，再让团队边界与它对齐（反向康威）；每个边界只有一个责任人和一个接口人，跨组约定只走契约、决策日志（ADR）与评审，不走口头；知识沉淀为带负责人与复核日期的单一权威源，让新人靠文档和可运行的脚本上手，而不是靠问人。

> 层级：L5 交付与协作 ｜ 对应痛点：新人上手慢、知识靠口口相传；技术债积压、不敢重构；多小组协作的边界与接口 ｜ 来源：本文扩展（概念呼应原文《领域建模与职责边界》《契约优先》《演进式架构与 YAGNI》）

## 为什么需要它

10 人以上、多小组之后，沟通路径迅速增多。边界不清的模块人人都能改、无人负责，债务无人偿还；决策与约定只存在于口头和聊天记录，老人一走就失传，新人只能靠问。对应「新人上手慢、知识靠口口相传」「技术债积压、不敢重构」，以及多小组协作中「改了别人的东西没人知道」。

## 核心主张

- 康威定律（Conway's Law）说系统结构会映射组织的沟通结构；所以反过来用：先按变化原因定系统边界（见 02、03），再让团队与它对齐，而不是让现有汇报线决定模块怎么切。
- 一个边界一个责任人：每个模块、契约、配置域、文档都有责任人（owner）与接口人；无主资产是技术债的温床。
- 认知负荷有上限：平台组提供扩展接口与自助工具，机台组不必读懂内核内部才能工作。
- 约定只有落成可检查的载体才算数：接口落契约（见 08），决策落 ADR，术语落术语表；口头约定的有效期是下一次人员变动。
- 同一事实只在一处维护，其余地方只引用名称；每份权威文档有负责人与复核日期，过期未复核就降级标记。
## 怎么做

1. 先画系统边界图，按变化原因划分（见 02）。Slots 项目常见的划分：平台内核（加载、转轴驱动、音频、网络、资源）、机台组件、运营配置（活动规则与配置表，属于策略数据，见 04）、结算服务。
1. 让团队对齐边界，并为每个边界指定 owner 与接口人。接口人负责接收跨组请求并分派，不是所有问题的人肉路由；小团队可一人兼任多个角色，但边界在文档里仍然分开。职责划分示例见下表。
1. 跨组改动走属主评审：把目录与契约文件的属主写进仓库（用代码托管平台的目录属主评审机制，按所用平台核对）；改他组拥有的路径须经属主批准，改跨组契约须生产方与消费方双方会签（流程见 08）。
1. 设计评审按触发条件开，不凭感觉。命中任一条就必须评审：单向门决策（协议字段语义、账务数据结构、结算权威边界、存档与对外数据格式，见 01）；新增或修改跨组契约；引入内核层或平台层抽象，或落地第二个实现（R2、R5）；需两个以上小组配合的改动；性能或包体预算例外申请（见 12）。必备材料五项：背景与约束、备选方案与取舍、影响面与会签人、回滚或退出方式、验证计划（由哪个检查证明它成立）。
1. 决策落 ADR，只对单向门与跨组决策写，双向门快做不写（R4）。ADR 含背景、决策、后果、状态、替代方案五项；状态取 提议 / 已接受 / 已取代 / 已废弃；已接受的 ADR 不原地改写，只能被新 ADR 取代。模板见 A2。
1. 维护统一语言术语表：每词条写词、所属上下文、定义、禁用同义词、负责人；同一个词在不同上下文含义不同时分条写（如「下注」，见 02）。
1. 单一权威源与过期治理：为契约、决策、术语、上手指引各指定唯一权威位置；每份权威文档头部写 owner、状态与复核日期（见下方示例），CI 定时扫描过期项并通知 owner；复核周期由团队约定。
1. 技术债登记与偿还：每条债务登记位置、影响哪类痛点、触碰成本（每次改它多花什么）、偿还触发条件；偿还遵循「先补安全网（特征化测试、回放对账）再重构」（见 10）；每个迭代为偿还预留固定容量，比例由团队约定；影响资金安全、合规或不可逆数据的债务优先（R1）。
1. 代码评审清单化：把适用的问句放进 PR 模板；能自动检查的一律进 CI（R6），人工评审只留判断类问题。
1. 新人上手按下方首周路径走，并让每个新人把踩到的坑补回文档。
职责划分示例（小组划分为示例，按本公司实际组织调整）：

| 小组 | 拥有 | 不拥有 | 接口人负责 |
| --- | --- | --- | --- |
| 平台组 | 平台内核、扩展接口、共享工具链与质量门 | 任何一款机台的玩法表现与活动规则 | 评审扩展接口变更；发布内核版本说明 |
| 机台组 | 某款机台的组件、Prefab 与资源包 | 内核源码、协议与配置 schema | 向平台组提扩展诉求；维护本机台 README 与债务登记 |
| 服务端组 | 结算与账务、协议实现、服务端配置校验 | 客户端表现与活动文案 | 协议契约会签；提供 mock 与录制回放 |
| 运营组 | 活动规则等策略数据、文案与皮肤配置 | 机制代码；高危配置的单人发布权（须双人复核，见 05） | 按配置管线提交变更；维护活动相关术语 |

权威文档头示例（字段为示例，按团队约定）：

```yaml
title: 机台资源命名规范
owner: 机台组接口人
status: 已接受            # 提议 / 已接受 / 已取代 / 已废弃
authority_for: 资源命名与目录
last_reviewed: 2026-10-01
review_every_days: 90     # 示例值，按团队约定
superseded_by: ""
```

新人首周路径（示例，按团队调整）：

| 阶段 | 读什么 | 跑什么 | 改什么 |
| --- | --- | --- | --- |
| 第 1 天 | 总纲与规则 R1 到 R7、术语表、系统边界图 | 上手脚本：从克隆到在测试环境跑通一款机台 | 不改代码，记录脚本里任何卡住的地方 |
| 第 2 到 3 天 | 平台内核与所在机台的 README、关键 ADR、契约仓库中的 Spin 协议 | 测试环境完整 Spin 链路；回放一条录制，查看对账日志（见 09） | 改一处低危配置（文案或皮肤）并走完内容管线（见 13） |
| 第 4 到 5 天 | 本组债务登记表、A1 评审清单 | 本组 CI，读懂一条失败报告 | 提交一个小 PR：偿还一条低风险债务或修一处过期文档，经属主评审合入 |

首周交付物三件：上手脚本的偏差记录；一个合入的 PR；向术语表或上手文档补一条自己踩到的坑。

## 在 Slots / Cocos 项目里的落地

| 场景 | 做法 | 反例 |
| --- | --- | --- |
| 平台组与机台组（内核与机台） | 机台组只经内核扩展接口与事件接入，内核 owner 评审接口变更；第三款机台前先复制、再抽取（R2） | 机台组「顺手」改内核源码，内核成了各机台补丁的堆；机台之间互相 import |
| 运营组与程序（活动规则、配置） | 运营组改策略数据，程序改机制（判别问句见 04）；活动规则走配置管线发布（见 13），无需程序发版 | 活动规则写进代码，每次活动都要程序发版 |
| 客户端与服务端（Spin 协议联调） | 协议契约双方会签，用 mock 与录制回放并行开发（见 08）；联调出问题先查契约与管线报告 | 群里口头约定字段含义，各自理解，联调时互相指责 |
| 老机台遗留与技术债 | 债务登记在册；动老机台前先补特征化测试或回放对账（见 10）；每次触碰顺手偿还一小块 | 「不敢动」的模块无人认领，所有人绕着走，补丁叠补丁 |
| 新人上手 | 上手脚本一键拉起测试环境并跑通 Spin 链路，首周提交一个小 PR | 新人靠问人拼凑环境，一周后仍无法本地跑通 |

## 评审清单

| 评审类型 | 检查问句 | 不通过信号 |
| --- | --- | --- |
| 设计评审 | 本设计涉及的每个模块、契约、配置域是否都有 owner 与接口人？ | 出现「大家共同维护」或「待定」的归属 |
| 设计评审 | 跨组边界改动（协议字段、扩展接口、配置 schema）是否附契约变更单并有消费方会签？ | 只在群里通知，没有会签记录 |
| 设计评审 | 属于单向门的决策是否附 ADR，且含替代方案与后果？ | 方案文档只有结论，没有替代方案与后果 |
| 设计评审 | 他组使用本模块时，是否无需阅读其内部实现即可接入？ | 接入方必须读源码或来问人才能用 |
| 设计评审 | 新增概念是否进入术语表，并与同词异义的既有术语区分？ | 同一个词在文档里有两种用法 |
| 设计评审 | 本设计是否命中设计评审触发条件？命中的是否备齐五项材料？ | 命中却直接开发；材料缺回滚方式或验证计划 |
| 代码评审 | PR 触及他组属主路径时，是否已有属主批准？ | 绕过属主合并，合并后才通知 |
| 代码评审 | 含不兼容改动的 PR 是否引用契约变更单或 ADR？ | PR 描述只写「优化」「重构」 |
| 代码评审 | 新增的 TODO 或临时绕过是否带债务登记编号？ | 无编号 TODO，无负责人 |
| 代码评审 | 代码变更影响的权威文档（README、术语表、上手路径）是否同步更新并刷新复核日期？ | 代码已变，文档复核日期已过期 |

## 误用与反模式

- 按现有汇报线切模块：组织怎么分，模块就怎么分，边界随人事调整而抖动；应先定系统边界。
- 平台组变成需求排队的工单窗口：机台组每个改动都要平台组代做，平台组成了瓶颈；应提供扩展接口和自助工具，抽取节奏按 R2。
- 文档只增不管：同一事实复制多处，无 owner、无复核日期，沉淀「有空再做」；过期文档比没有文档更危险。
- ADR 事后补成流水账或甩锅记录：没有替代方案与后果的 ADR 没有信息量；连双向门也写 ADR，会稀释真正重要的决定（R4）。
- 全员会签：所有改动都要所有小组同意，评审变成瓶颈；只对跨组契约与单向门会签。
## 取舍与边界

- 小团队不必全套：单一小组、一人维护多个模块时，保留 owner 标注、术语表与单向门 ADR，省略接口人制度与过期扫描（R3：未跨团队不冻结）。
- 反向康威不是一次重组：调整组织成本高。先在现有组织内用「属主加接口人」模拟目标边界，稳定一段时间后再考虑调整团队划分。
- 与 10 的张力：债务登记不等于都要还。按 R1 排序，影响不可逆数据、合规、资金安全的债务优先于只影响结构整洁的债务，偿还前先建安全网。
- 与 11 的张力：评审清单中能自动化的进 CI（R6），人工评审只保留需要判断的问题，避免清单越写越长、无人逐条核对。
- 与 08、R4 的分工：08 管契约怎么写、怎么变，本卡管谁拥有、谁会签；ADR 只为单向门与跨组决策写，双向门快做，写进提交说明即可。
## 可执行的检查

| 检查项 | 执行位置 | 判定标准 |
| --- | --- | --- |
| 属主覆盖：每个顶层目录与契约文件都有属主记录 | 提交（属主文件变更时）+ CI | 无属主的路径数为 0 |
| 文档头完整性：权威文档含 owner、状态、复核日期 | CI | 缺任一项即失败 |
| 过期扫描 | CI（定时） | 复核日期超过自身声明周期的文档列出并通知 owner；连续两个周期未处理则标记过期并移出上手路径（示例规则，按团队约定） |
| 契约变更会签：修改契约目录的 PR 须引用变更单，且生产方与消费方 owner 均已批准 | CI + 评审平台 | 缺任一项即阻止合并 |
| ADR 不可原地改写 | CI | 已接受 ADR 的正文被修改即失败，只允许改状态与 superseded_by；被取代的 ADR 必须指向后继 |
| 债务登记：新增 TODO 或 FIXME 须带登记编号 | 提交钩子 + CI | 无编号的新增数为 0 |
| 上手脚本：在干净环境从克隆到跑通测试环境 Spin 链路 | CI（定时）+ 新人入职时由其亲自走一遍 | 脚本退出码为 0 且无人工介入；新人记录的偏差在下个迭代内修复或登记 |
