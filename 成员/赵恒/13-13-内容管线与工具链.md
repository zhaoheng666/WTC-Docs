# 13 内容管线与工具链

> 源自飞书文档 · 最后同步：2026-10-30

**一句话**：内容管线要让策划、美术能自己安全地改东西：每类内容有机器可校验的 schema 或规范，错误在离作者最近的关口（编辑器、导出器、提交钩子、CI、发布前）被自动拦下，客户端包、资源、配置、服务端四类版本由一张兼容矩阵约束；联调以管线报告定责，不以口头为准。

> 层级：L5 交付与协作 ｜ 对应痛点：策划、美术、程序、服务端联调扯皮；配置或数值出错、线上事故 ｜ 来源：本文扩展（概念呼应原文《契约优先》《领域建模与职责边界》）

## 为什么需要它

策划改数值表，美术交图集与骨骼动画，程序改代码，服务端改规则，四方产出在同一条链路上交汇。没有管线时，格式错误、引用悬空、版本错配要到联调甚至线上才暴露，且无法判定是谁的输入不合规，于是扯皮；高危配置出错则直接成为线上事故。管线要把「谁的错、错在哪」变成机器可回答的问题。

## 核心主张

- 管线是契约的执行者：每类内容都有 schema 或规范文件（见 08、05），人只负责产出，不负责肉眼检查。
- 校验越早越好：能在编辑器拦的不留给导出器，能在提交钩子拦的不留给 CI；每后移一关，涉及的人和环境就更多。
- 规则只实现一次：编辑器、提交钩子、CI 调用同一个校验器，禁止「本地一套、CI 一套」（R6）。
- 版本矩阵是一等产物：任一发布都能回答「这个客户端包能搭配哪些资源、配置与服务端版本」，兼容关系写在清单里。
- 工具也是产品：校验器、导出器、编辑器扩展有契约、测试、版本号和负责人，不是某位程序的私人脚本。
## 怎么做

1. 登记内容类型：配置与数值表、图集 / 骨骼 / 粒子 / 音频、客户端代码与编辑器扩展、服务端规则与协议实现，每类写清产出方、消费方、规则文件位置和风险等级（分级见 05）。
1. 规则进 Git：schema 与资源规范随仓库版本化，改规则走 PR，产出方与消费方双方会签（R3：跨团队即冻结，流程见 08）。
1. 编辑器 / 导出器关：单文件即时反馈（字段范围、枚举、命名、尺寸），并提供预览；预览加载的必须是与线上同一份导出产物。
1. 提交钩子关：只检查本次变更的文件，目标是几秒内返回，不在这里跑全量模拟。
1. CI 关：全量校验，包括引用完整性、权重和与概率和、跨表一致性、与代码版本兼容、契约破坏检测、模拟跑数回归、包体与预算（见 11、12）。
1. 发布关：版本矩阵校验，灰度放量，自动回滚阈值（见 11）。
1. 一键构建：同一条命令在干净环境、固定工具版本下产出客户端包、资源包、配置包与版本清单，产物写入版本号与来源提交；禁止手工拷贝。
1. 环境隔离：开发、测试、预发、生产使用独立的配置包与服务端地址；配置包头部写环境标识，加载时核对，不一致就拒绝并上报；生产密钥与地址不进内容仓库。
1. 维护版本矩阵：四类版本各自独立编号，不共用总版本号；兼容关系用 `requires`（我至少需要对方什么版本）与 `accepts`（我接受对方哪些版本）声明写入清单。发布顺序遵循「接收方先兼容新旧两种，发送方后切换」，回滚按相反顺序（按所用热更与发布机制核对）。
1. 联调以管线报告定责：校验失败，归产出方修；校验通过但联调仍出错，说明规则有缺口，由规则负责人补规则并按 11 的事故闭环沉淀检查；契约没覆盖的约定，转入契约变更流程（见 08）。
版本清单示例（示例值，不是任何现有系统的格式）：

```json
{
  "release": "示例-0001",
  "client":   { "version": "1.8.0", "min_config_schema": 7, "min_resource": 120 },
  "resource": { "version": 123, "min_client": "1.8.0" },
  "config":   { "version": 42, "schema": 7, "env": "prod", "content_hash": "构建时写入" },
  "server":   { "version": "3.2.1", "accepts_config_schema": [6, 7] },
  "checks":   ["schema", "refs", "weights", "sim-regression", "budget", "contract-diff"],
  "approved_by": ["策划复核人", "数值复核人"]
}
```

## 在 Slots / Cocos 项目里的落地

| 场景 | 做法 | 反例 |
| --- | --- | --- |
| 策划改赔付表、卷轴带 | 导出器按 schema 校验范围、枚举与引用；高危表变更触发模拟跑数并要求双人复核；若产品涉及真实资金或受监管，以服务端持有的配置为准，客户端只展示 | 直接改表格提交，错误到联调才暴露；客户端与服务端各留一份数值，两边悄悄不一致 |
| 美术交付机台图集、骨骼、粒子、音频 | 规范写成脚本（示例：命名 `机台代号_类别_名称`，目录按机台分，尺寸上限按目标机型实测），提交钩子增量检查；Prefab 与资源引用在 CI 扫描悬空；Cocos Creator 的构建流程与编辑器扩展可作为检查入口（按所用版本核对） | 规范只在文档里，靠美术组长肉眼审；资源散落在随手建的目录 |
| 机台 Asset Bundle 与热更 | 每个 bundle 在清单里声明所需客户端最低版本与配置 schema 版本，发布前跑矩阵校验 | 资源包随手上传，客户端加载时才发现配置缺字段（热更包与配置不匹配） |
| 测试、预发、生产多环境 | 配置包带环境标识，加载时核对；构建与发布在干净环境一键完成 | 手工改地址后把测试配置包当生产包上传（环境混用） |
| 策划即时预览 | 预览工具加载与线上同一份导出产物，改表后能在测试环境用固定随机种子跑一局模拟 Spin（见 09） | 预览走另一套手写 JSON，预览正常、线上异常 |

## 评审清单

| 评审类型 | 检查问句 | 不通过信号 |
| --- | --- | --- |
| 设计评审 | 新增内容类型（新表、新资源类别）是否登记了产出方、消费方、规则文件位置和风险等级？ | 只有口头约定，「问某某就知道格式」 |
| 设计评审 | 每类校验是否标明执行关口，且能前移的已前移？ | 校验全堆在 CI，或靠测试同学手测 |
| 设计评审 | 是否有版本矩阵：四类版本各自编号，兼容方向、发布顺序、回滚顺序都写明？ | 只有一个总版本号，或「一起发就行」 |
| 设计评审 | 高危配置（金额、概率、赔付）是否规定双人复核与模拟回归；若产品涉及真实资金或受监管，是否以服务端为准？ | 高危表与文案表走同一条流程 |
| 设计评审 | 环境标识与隔离是否设计到加载时核对？ | 靠文件名或人的记忆区分环境 |
| 设计评审 | 校验器与导出器是否有负责人、版本号与自测？ | 校验脚本在某人本机，换人即失效 |
| 代码评审 | 新增或修改的校验规则是否同时带「应通过」与「应失败」样例？ | 只有通过用例，规则是否生效无人知道 |
| 代码评审 | 提交钩子与 CI 是否调用同一个校验入口？ | 规则逻辑被复制两份，两边判定不一致 |
| 代码评审 | 业务代码是否经生成的常量或类型引用资源与配置键，而不是直接写路径或键名字符串？ | 魔法字符串，改名后运行时才暴露 |
| 代码评审 | 构建脚本能否在干净环境一键复现，产物是否带版本号与来源提交？ | 构建依赖某台机器的本地状态 |
| 代码评审 | 含不兼容的 schema 变更时，同一 PR 是否包含迁移脚本、清单与矩阵更新？ | 改了字段语义，版本号不变 |

## 误用与反模式

- 规范只写在文档里：没有对应检查脚本的规范等于没有（R6）。
- 校验全部后置到 CI：策划提交后才得知字段拼错，来回往返；该前移的没前移。
- 管线变成人工瓶颈：非程序员每次改表都要找程序「导表」，自助变排队，大家反而绕过管线。
- 过早建设通用内容平台：还没有第三类相似内容就做万能可视化编辑器或通用 DSL（R2、R5）；先让最痛的一类（高危配置）跑通。
- 预览与线上走两条路径：预览通过不代表线上通过。
- 规则豁免不留痕：为赶发布放宽检查却不登记负责人和到期日，临时豁免会变成永久漏洞。
## 取舍与边界

- 不必全套：单人原型期、内容类型少于两类且只有一人改动时，保留 schema 与一键构建即可，四道关口不必齐备（R3：单人单模块内不冻结）。
- 与 11 的张力：新增关口要有真实事故或风险支撑，误报高的检查先降为告警并设到期日；速度与覆盖冲突时，快的前移，慢的（全量模拟）留在 CI 且不得绕过。
- 与 05 的分工：05 管配置本身的分级、schema 与灰度，本卡管承载它的流水线与多角色协作；预算阈值来自 12，本卡只负责把检查挂进关口。
- 紧急热修：可走加急通道缩短流程，但高危配置的关口不得跳过，事后补登记；依据 R1，资金安全与合规高于发布速度。
- 版本矩阵：机台少、发布集中时，一份清单加一条校验脚本即可，不要提前建设版本管理平台（R2）。
## 可执行的检查

| 检查项 | 执行位置 | 判定标准 |
| --- | --- | --- |
| 配置 schema 校验（类型、范围、枚举、必填） | 导出器 + 提交钩子 | 任一字段不符即失败；豁免须登记负责人与到期日 |
| 引用完整性（配置到资源、Prefab、其他表） | 提交钩子 + CI | 悬空引用数为 0 |
| 权重和、概率和与跨表一致性 | CI | 偏差在 schema 声明的容差内；容差写进 schema，不写在脚本里 |
| 模拟跑数回归（高危表变更触发） | CI + 发布前 | 命中率与回报率在该机台声明的容差内，并输出与上一版本的差异报告，由复核人签字（容差由数学模型方给出，见 09） |
| 资源规范检查（命名、目录、尺寸上限、格式、图集规则） | 提交钩子（增量）+ CI（全量） | 违规资源数为 0；白名单项带负责人与到期日（上限值为示例值，须按项目实测设定） |
| 版本矩阵校验（清单中 requires 与 accepts 互相满足） | 发布前 | 发布集中任一组合不满足即阻止发布；回滚目标版本同样通过校验 |
| 环境标识核对 | 线上（加载时）+ 发布前 | 配置包环境标识与运行环境不一致即拒绝加载并上报 |
| 校验器自测与可复现构建 | CI（定期） | 每条规则有通过 / 失败样例且结果符合预期；同一提交两次构建的文件清单与内容哈希一致（做不到逐字节一致时退化为清单一致，按所用构建工具核对） |

## 来源与扩展

- 无直接对应原文，本卡均为本文扩展，概念与原文保持一致：原文《契约优先》的「契约进 Git、CI 做破坏性变更检测、一旦跨团队立刻冻结、用 Mock 让各方并行」，落到各类内容的 schema 与规范文件；原文《领域建模与职责边界》的「同一个词在不同上下文含义不同」，提示管线要有统一语言，「配置」「资源」「版本」在各角色口中的含义需对齐（术语表见 14）。
- 本文扩展：四道关口与校验前移、版本矩阵与 requires / accepts 声明、环境标识核对、联调以管线报告定责、工具的契约 / 测试 / 版本要求。
- 需按实际核对：Cocos Creator 编辑器扩展与构建钩子的具体接口与能力（按所用版本核对）；资源压缩格式、图集规范与各类数值上限均为示例，按目标机型与平台实测设定；热更新与分包的平台规则（按平台要求核对）；模拟跑数容差，以及配置变更留痕、测试的合规与认证要求（按所在辖区 / 认证机构要求核对）；版本清单字段为示例。
