# 07 依赖倒置与适配器

> 源自飞书文档 · 最后同步：2026-10-30

**一句话**：由领域层定义端口、适配器翻译外部实现，让依赖方向指向领域而不是渠道 SDK；但只在出现第二个真实实现或真实隔离需求时才引入端口（见规则 R2），官方服务与引擎 API 仍是权威，不为它再包一层完整宿主。

> 层级：L3 接缝 ｜ 对应痛点：多项目或多款游戏复用困难；需求频繁变更导致返工（换渠道、换 SDK）；技术债积压、不敢重构 ｜ 来源：原文《依赖倒置与适配器》

## 为什么需要它

多渠道、多款机台复用时，若玩法与商店代码直接调用某渠道 SDK，换渠道或升级 SDK 就要改到业务深处，测试还必须连真机沙箱。把「需要什么」收敛成领域层的端口，外部差异关进适配器，变化就被圈在一处，玩法也能脱离 SDK 单独运行与测试。

## 核心主张

- 依赖倒置原则（DIP，Dependency Inversion Principle）是战略：高层不依赖低层，两者都依赖抽象；适配器模式（Adapter）是战术：把外部接口翻译成领域想要的接口。
- 端口（Port）由使用方，也就是领域层，按自身需要定义，不照抄任何 SDK 的形状。
- 适配器只做翻译：字段、单位、状态、错误的映射；不放业务规则。
- 外部模型与领域模型差异大时，适配器升级为防腐层（ACL，Anti-Corruption Layer），承担深度的语义与结构映射。
- 不为适配而适配：SDK 已天然满足端口、或是团队内部可控模块，直接依赖，不套空壳。
## 怎么做

1. 先找真实变化：这个外部依赖有几个渠道或实现？是否需要在测试中脱离它？说不出就先直接依赖（规则 R2、R5）。
1. 从玩法需求出发写端口：方法按领域语言命名，并写明失败、取消、超时与幂等语义（见 08）。
1. 为每个外部实现写适配器，实现同一端口；适配器内完成单位换算、字段改名、状态与错误码映射。
1. 外部状态机与领域差异大（如支付订单状态）时，显式按防腐层设计，并登记映射表与未知状态的处理方式。
1. 在装配处（组合根）按渠道、环境选择适配器；业务代码里不出现渠道判断。
1. 为端口提供内存实现的测试替身，并让同一套契约测试同时跑真实实现与替身。
```typescript
// 端口（领域层定义）：支付有取消与待确认，布尔不够
export type PurchaseResult =
  | { status: "success"; orderId: string }
  | { status: "cancelled" | "failed" | "pending"; reason?: string };
export interface PaymentPort {
  purchase(playerId: string, priceCents: number, sku: string): Promise<PurchaseResult>;
}
// 适配器（示例：SDK 不可修改）：只做翻译
export class ChannelAPayment implements PaymentPort {
  constructor(private sdk: ChannelASdk) {}
  async purchase(playerId: string, priceCents: number, sku: string): Promise<PurchaseResult> {
    const r = await this.sdk.pay({ uid: playerId, amount: priceCents / 100, item: sku });
    return r.code === 0 ? { status: "success", orderId: r.tradeNo }
      : { status: r.code === 1 ? "cancelled" : "failed", reason: r.msg };
  }
}
```

若产品涉及真实资金或受监管，支付与账务结果以服务端为准（见 09），客户端适配器只负责发起与回传，不据此自行入账。

## 在 Slots / Cocos 项目里的落地

| 场景 | 做法 | 反例 |
| --- | --- | --- |
| 支付、内购 | 商店上下文定义 PaymentPort，各渠道一个适配器；订单状态差异大的渠道做防腐层映射 | 商店面板直接调用渠道 SDK，SDK 的状态值散落在界面里 |
| 登录、广告、推送、埋点 | 各自一个端口；埋点端口只暴露领域事件（如一局结束），不暴露统计 SDK 的事件名 | 玩法代码到处直接调用 SDK 的上报函数 |
| 引擎的存储、网络、音频接口 | 只在不稳定或需要替身之处加薄接缝；引擎 API 仍是权威，不另造一套 | 包一层「万能引擎抽象」，承诺将来跨引擎通用 |
| 玩法测试 | 内存实现的假支付、假存档，让玩法测试不启动 SDK 与引擎 | 玩法单测必须连渠道沙箱才能跑 |
| 多渠道包 | 在启动装配处选适配器，渠道差异只存在于适配层 | 玩法代码里写渠道名的分支判断 |

## 评审清单

| 评审类型 | 检查问句 | 不通过信号 |
| --- | --- | --- |
| 设计评审 | 端口是否由领域层按玩法需求定义，而不是 SDK 的形状？ | 端口方法名与参数照抄某个 SDK |
| 设计评审 | 引入端口是否有第二个真实实现或测试替身需求（规则 R2、R5）？ | 理由只是「以后可能换」 |
| 设计评审 | 外部模型差异大时，是否明确为防腐层并写了映射表？ | 外部状态值原样透传进领域 |
| 设计评审 | 端口是否写明失败、取消、超时、幂等语义？ | 只有方法名，没有错误约束 |
| 设计评审 | 官方服务与引擎 API 的权威边界是否明确？ | 适配层自行缓存或改写权威结果 |
| 代码评审 | 领域层是否引用了 SDK 或引擎模块的类型？ | 领域代码里出现 SDK 包名 |
| 代码评审 | 渠道、环境判断是否只出现在装配处？ | 业务代码里出现渠道分支 |
| 代码评审 | 适配器里是否混入业务规则？ | 适配器里计算价格、判断活动资格 |
| 代码评审 | 是否存在只转发、无翻译价值的空适配器？ | 适配器每个方法都是一行原样透传 |

## 误用与反模式

- 为适配而适配：SDK 已满足自定义接口，或是团队内部可控模块，仍套一层空壳。
- 端口照抄 SDK：形式上依赖了接口，实质仍依赖 SDK 的形状，换渠道时端口也得改。
- 再包一层完整宿主，追求尚不存在的跨平台通用性：官方服务与引擎 API 才是权威，不是被你取代的对象。
- 适配器塞业务规则：它变成第二个领域层，且无法被测试替身替换。
- 抽象泄漏：适配器把 SDK 的异常与错误码原样抛进领域，或让领域层拿到 SDK 类型。
## 取舍与边界

- 不用或延后：外部依赖稳定且只有一个实现、没有测试痛点；内部可控模块；一次性原型。
- 测试替身算不算第二个实现：当它解决了真实的测试或联调痛点时算，因为被真实需求证明（规则 R5）；仅为「万一」不算。
- 与 03：小内核里组件之间不直接引用，经内核通道或端口通信；端口是领域层定义的抽象，内核通道是机制。
- 与 08：端口只是形状，契约还包含语义；契约冻结时机按规则 R3，单模块内的端口不必冻结。
- 与 06：热路径内不要为抽象多加间接层，端口放在元层与外部服务之间。
- 裁决：规则 R2 决定何时引入，规则 R5 要求举证；若与 R1 冲突，涉及真实资金或合规的外部依赖（支付、实名认证类）可在第二个实现出现前先建端口，但须登记理由（规则 R4）。
## 可执行的检查

| 检查项 | 执行位置 | 判定标准 |
| --- | --- | --- |
| 依赖方向检查：领域目录禁止引用 SDK 包与引擎模块 | 提交 / CI | 领域层出现外部引用则失败 |
| 渠道、环境判断扫描 | CI | 渠道常量的条件判断只允许出现在装配目录 |
| 适配器契约测试：同一套用例跑真实（沙箱）与内存替身 | CI（沙箱用例可夜间跑） | 两种实现行为一致，用例全部通过 |
| 空适配器巡检：只转发、无转换与映射的适配器 | 评审 / 定期 | 命中者须说明保留理由，否则列入删除候选 |
| 防腐层未知状态计数 | 线上 | 出现未映射的外部状态即告警（阈值按项目设定） |

## 来源与扩展

- 来自原文《依赖倒置与适配器》：DIP 为战略、Adapter 为战术；六边形架构（端口与适配器）；端口由业务层定义；防腐层与适配器的关系；「不要为了适配而适配」；支付示例（本卡改写压缩，并把成功与否的布尔值改为含取消、待确认的状态，原文示例没有失败与取消语义）。
- 来自根文档对照表：用少量接缝隔开领域组件与外部接口，官方服务仍是权威；误用是再包一层完整宿主、追求尚不存在的跨平台通用性。对照表的原语境不是游戏，本卡的迁移属本文扩展。
- 本文扩展：Slots 端口举例、装配处选渠道、契约测试、测试替身与规则 R2 的裁决、热路径与端口的关系。
- 需按实际核对：各渠道 SDK 的订单状态集合与失败语义；支付、内购的平台审核要求（按平台与渠道要求核对）；实名、合规认证接口（按所在辖区与认证机构要求核对）；引擎存储、网络、音频 API 按所用版本核对。
