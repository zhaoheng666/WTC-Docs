# 05 数据驱动与配置治理

> 源自飞书文档 · 最后同步：2026-10-30

**一句话**：数据驱动的前提是把配置当代码治理——每份配置有 schema、版本、校验、评审、灰度与回滚；金额、概率、赔付这类高危配置还须模拟回归并以服务端为准；同时「可配」有边界，只有被真实变化证明的策略才做成数据。

> 层级：L2 切分 ｜ 对应痛点：配置或数值出错、线上事故；需求频繁变更导致返工；策划、程序、服务端联调扯皮 ｜ 来源：本文扩展（承接 04 机制与策略分离）

## 为什么需要它

04 把「做什么」下放为策略数据，配置因此成了线上行为的直接来源：赔付表、卷轴带、活动规则一改，玩家看到的结果就变。配置出错编译器拦不住，却能直接造成事故；没有版本与追溯，联调时也说不清「到底是哪一版」。需求越频繁，越要把改动关进有校验、有灰度、可回滚的通道。

## 核心主张

- 配置即代码（Configuration as Code）：进版本库、有 schema、走评审，不留「改完直接上线」的带外通道。
- 按风险分级治理，不一刀切：高危（金额、概率、赔付）、中危（活动规则）、低危（文案、皮肤）门槛不同，排序遵循规则 R1。
- 校验越早、越机械越好：校验器能判定的不交给人眼，底线交给 CI（见规则 R6）。
- 高危配置以服务端为准：客户端只持只读快照，不自行计算概率与金额（见 09）。
- 数据驱动不等于万物可配：每个配置项要说得出被哪个真实变化证明（见规则 R5），说不出就不开放，否则会长成难以调试的隐形 DSL。
## 怎么做

1. 先登记再治理：每张配置表登记风险等级、负责人、变更频率与权威方（服务端或客户端）。
1. 写 schema：字段类型、范围、枚举、必填、引用关系、版本号与最低兼容的代码版本。schema 与代码同库、随版本发布，本身就是契约（见 08）。
1. 校验分层：编辑器与导出器做字段级即时校验；提交钩子与 CI 做全量校验，包括范围、枚举、引用完整性、权重和或概率和、跨表一致性、与代码版本兼容。
1. 高危配置加跑模拟回归：变更后批量模拟，验证命中率与回报率（Return To Player，RTP）落在预期容差内；容差由数学模型方给出并登记（见 09、11）。
1. 评审按级：高危双人复核，其中至少一人来自数值或服务端；中危一名评审；低危通过自动检查即可。
1. 发布即版本：每次发布产出不可变版本号与变更单，分阶段放量，指标越线回滚到上一版本（见 11）。
1. 可追溯：线上请求与埋点携带配置版本号，事故时能回答「当时生效的是哪一版」。
```yaml
# 示例：某张赔付表的治理登记与 schema 片段
table: paytable
risk: high                  # high / medium / low
owner: 数值策划
authority: server           # 以服务端为准
schema_version: 3
min_code_version: "1.8.0"   # 示例值
fields:
  symbol: { type: enum, values: [A, B, C, WILD] }
  count:  { type: int, min: 3, max: 5 }
  payout: { type: int, min: 0 }
checks:
  - unique: [symbol, count]
  - ref_exists: "symbol -> symbol_table.id"
  - weight_sum: "reel_strips 每条权重和等于声明的目标和"
  - sim_regression: { rounds: N, tolerance: "由数学模型方给出" }
```

## 在 Slots / Cocos 项目里的落地

| 场景 | 做法 | 反例 |
| --- | --- | --- |
| 赔付表、卷轴带、权重 | 高危档：schema、权重和校验、模拟回归、双人复核，以服务端为准；客户端只用于表现 | 策划改完数值表，直接打进热更包上线 |
| 活动规则（开关、时间窗、奖励档位） | 中危档：时间窗与引用完整性校验，带灰度开关，可回滚 | 活动 ID 写死在代码的 if 里（策略泄漏进机制，见 04） |
| 文案、皮肤、音效挂接 | 低危档：资源引用检查自动化，通过即发布 | 一句文案也走高危全流程，拖慢迭代 |
| 热更包与配置 | 包版本、资源版本、配置版本在发布清单里声明兼容范围，启动时自检 | 热更包先到、配置后到，客户端用新代码读旧字段 |
| 测试、预发、正式环境 | 配置源带环境标识，发布工具拒绝跨环境直发 | 测试环境的概率表被带进正式环境 |

## 评审清单

| 评审类型 | 检查问句 | 不通过信号 |
| --- | --- | --- |
| 设计评审 | 这张表是否登记了风险等级、负责人和权威方？ | 说不出等级；改数值的人自己说了算，无人复核 |
| 设计评审 | 新增的可配项能否说出被哪个真实变化证明（见规则 R5）？ | 理由是「以后可能要调」 |
| 设计评审 | 高危配置是否定义了模拟回归的通过标准和容差来源？ | 容差无人认领，只靠人眼看数 |
| 设计评审 | 代码、资源、配置、服务端之间的版本兼容关系是否有声明？ | 四方各自发版，互不知道对方版本 |
| 代码评审 | 配置是否经 schema 校验后才进入业务代码？ | 业务代码到处是 config.xxx 加默认值兜底 |
| 代码评审 | 读取配置的代码里有没有活动 ID、渠道、环境的判断？ | 出现即策略泄漏（见 04） |
| 代码评审 | 配置变更是否经 PR，带变更说明与版本号？ | 直接覆盖线上文件，无法追溯 |
| 代码评审 | 客户端是否持有或改写了高危配置的权威值？ | 客户端本地计算概率或金额 |

## 误用与反模式

- 万物可配：把流程分支、动画时序都做成配置，最终长成隐形的领域专用语言（DSL），调试要靠猜（与 04 对「通用工作流 DSL」的告诫一致）。
- 带外通道：表格直接发到线上，绕过 schema 与评审，理由是「就改一个数」。
- 只校验格式不校验语义：类型对、范围对，但权重和不对、引用悬空。
- 缺字段静默回落默认值：把引用悬空变成线上悄悄生效的错误行为。
- 版本与环境混用：同一配置库不标环境；热更包与配置不同步；类型随手改（整数变字符串）而无人察觉。
## 取舍与边界

- 不用或延后：原型期、单人单机台、尚无稳定变化点时，常量写在代码里；第三次变化才抽成配置（见规则 R2、R5），一次性常量不建配置表。
- 与 04：04 划分哪些是策略，05 治理策略数据；不要为了「数据驱动」把机制也配置化。
- 与 08：schema 是契约的一种，跨策划、程序、服务端时按规则 R3 冻结。
- 与 09、11：高危配置的最后两道防线是服务端权威与模拟跑数，其余检查交给 CI（见规则 R6）。
- 裁决：R1 优先，高危配置宁可慢（复核加回归），低危配置宁可快（自动通过）。若产品涉及真实资金或受监管，变更留痕与复核要求通常更严，以所在辖区要求为准；社交或免费币类产品合规要求通常更轻，以实际要求为准，但仍建议服务端权威。
## 可执行的检查

| 检查项 | 执行位置 | 判定标准 |
| --- | --- | --- |
| schema 校验（类型漂移、范围、枚举、必填） | 编辑器 / 导出器与提交 | 任一字段违规则阻止提交 |
| 引用悬空与跨表一致性检查 | CI | 存在悬空引用或跨表冲突则失败 |
| 权重和、概率和校验 | CI | 与 schema 声明的目标和（含容差）不符则失败 |
| 模拟跑数回归（高危变更触发） | CI | 命中率或回报率偏离登记的容差则失败 |
| 版本错配与热更包匹配检查 | 发布前 | 配置要求的最低代码版本高于目标包版本则拒绝发布 |
| 环境混用检查 | 发布前 | 配置源环境与目标环境不一致则拒绝发布 |
| 灰度指标与自动回滚 | 线上 | 错误率或关键业务指标越线（阈值按项目设定）则回滚到上一版本 |

## 来源与扩展

- 本卡没有对应原文，属本文扩展。承接原文《机制与策略分离》（对应本系列 04）中「策略经配置注入」与「避免过度抽象」两点，并与原文《领域建模与职责边界》（对应 02）一致：配置 schema 归属各自上下文，不建全公司统一的万能配置表。
- 本文扩展：配置分级、校验清单、事故模式（引用悬空、类型漂移、版本错配、热更包与配置不匹配、环境混用）及对应检查、配置版本随请求携带。
- 需按实际情况核对：模拟回归的局数、命中率与回报率容差，由数学模型方与合规方确定；若涉及真实资金或受监管，配置变更的留痕、复核与认证要求按所在辖区和认证机构核对；热更与分包机制按所用 Cocos 版本核对；平台对热更的审核规则按平台要求核对；哪张表算高危由项目自行登记，本卡不给出固定名单。
