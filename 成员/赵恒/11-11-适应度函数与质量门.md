# 11 适应度函数与质量门

> 源自飞书文档 · 最后同步：2026-10-30

**一句话**：适应度函数（Fitness Function）是可自动执行的架构 / 质量底线检查；把结构、契约、数据、性能、体积、确定性六类底线按阶段放成质量门，用自动化而不是评审者的记忆守住它们（R6）。

> 层级：L4 演进与守护 ｜ 对应痛点：配置或数值出错、线上事故；性能、包体、加载超标；技术债积压、不敢重构 ｜ 来源：原文《演进式架构与 YAGNI》（适应度函数部分）+ 本文扩展

## 为什么需要它

边界、契约、性能和包体靠评审口头把关，团队一大就会漏；退化由一次次小改累积，没有人对某一次负责。线上事故复盘后常常只留下「下次注意」。要把底线变成能自动判定、能阻断的检查，并在出事后把教训固化成新的检查。

## 核心主张

- 底线必须可判定：每个适应度函数有明确输入、阈值和通过 / 不通过的结果，不写「尽量」。
- 按成本和反馈速度放置：越便宜越靠前（提交前），越贵越靠后（发布前），灰度期线上监控兜住前面测不到的。
- 六类检查：结构（依赖方向、禁止组件间直接 import）、契约（破坏检测）、数据（配置校验、模拟回归）、性能（帧时间、内存）、体积（包体、分包阈值）、确定性（回放一致性）。
- 灰度与回滚是质量门的一部分：开关、分阶段放量、自动回滚阈值。
- 门要有事实支撑：新增门需要真实事故或风险，并评估成本与误报；每次线上事故至少沉淀一条自动化检查。
## 怎么做

1. 盘点底线：从七类痛点里挑出已造成过返工或事故、且能机检的项，写入适应度函数登记表（模板见 A2）。
1. 提交前放秒级检查：格式、依赖方向、配置 schema 语法、单元测试。
1. CI 放分钟级检查：契约破坏检测（见 08）、配置引用完整性与概率和校验（见 05）、回放一致性与重复请求用例（见 09）。
1. 发布前放重检查：包体与分包阈值、性能基准（见 12）、配置变更后的模拟跑数（见 09）。
1. 灰度与线上：开关加分阶段放量，监控崩溃率、错误率和关键业务指标；回滚阈值提前约定，触发后自动执行，人工只做复核。放量比例与时长须按项目风险设定。
1. 每个门写明阈值来源、豁免人与豁免期限，失败输出要指出怎么修。
1. 事故复盘必须回答「沉淀了哪条自动化检查」；确实无法机检的，写明原因和替代的人工控制。
1. 每季度复核门的命中、误报与耗时；长期零命中且无风险支撑的门降级或删除。
```yaml
# 适应度函数登记示例（字段与取值均为示例，阈值须按项目设定）
- id: FF-pkg-size-first
  category: 体积
  stage: 发布前
  check: 首包体积不超过预算表上限
  threshold: 取自预算总表（见 12）
  on_fail: 阻断发布；例外需审批并登记偿还期限
  owner: 平台组
  origin: 事故复盘编号或风险登记编号   # 每个门必须有真实来源
```

## 在 Slots / Cocos 项目里的落地

| 场景 | 做法 | 反例 |
| --- | --- | --- |
| 模块边界 | 提交与 CI 检查机台组件之间禁止直接 import，只允许经内核接口通信（见 03） | 靠评审时看一眼，白名单越开越多 |
| 配置发布 | CI 做 schema、引用完整性与概率和校验，发布前对高危配置做模拟跑数（见 05、09） | 表格导出后直接上传，上线后才发现引用悬空 |
| 包体与加载 | 发布前生成分包体积报表并与预算比对，超限阻断（见 12） | 包体靠打包后人工翻看，临近发布才发现超标 |
| 热更与灰度 | 新包与新配置分阶段放量，按崩溃率、错误率与关键业务指标自动回滚 | 全量一次性推送，出问题靠人工撤回 |
| 事故复盘 | 每次事故产出一条自动化检查并登记来源 | 复盘结论是「加强培训」「下次注意」 |

## 评审清单

| 评审类型 | 检查问句 | 不通过信号 |
| --- | --- | --- |
| 设计评审 | 边界、契约、性能、包体各有对应的适应度函数吗？ | 只写「评审把关」「开发自觉」 |
| 设计评审 | 每个门是否写明放置阶段、阈值和失败后的处理人？ | 阈值是「尽量」「合理」，失败后无人负责 |
| 设计评审 | 灰度方案是否有开关、放量阶梯和自动回滚阈值？ | 回滚依赖人工判断，阈值临场再定 |
| 设计评审 | 新增门是否有真实事故或风险支撑，并评估了成本与误报？ | 理由是「看着应该有」，无来源 |
| 代码评审 | 改动是否放宽了阈值或新增白名单，规则变更是否单独评审？ | 同一个合并请求里既改功能又放宽阈值 |
| 代码评审 | 豁免项是否带原因、负责人和到期日？ | 永久豁免，没有注释 |
| 代码评审 | 事故修复的合并请求是否附带对应的自动化检查？ | 只修缺陷，不加回归检查 |

## 误用与反模式

- 门越多越好：每道门都增加耗时与误报，团队开始习惯性绕过，整体反而更不安全。
- 阈值拍脑袋或一次设死：阈值应来自预算与实测，并随版本复核（见 12）。
- 只在 CI 设门，不做灰度与线上监控：CI 测不到真机、真实数据与真实流量下的问题。
- 误报长期不处理：门退化成「红了就重跑」，失去信号意义。
- 复盘只归因于个人疏忽：这样的结论无法沉淀成检查。
## 取舍与边界

- 原型与一次性验证代码不必上全套门；优先给跨团队边界、资金与账务相关、体积与性能底线设门（R1、R6）。
- 门的严格度按风险分级：高危配置与账务相关检查阻断，低危（文案、皮肤）可只告警（R1）。
- 与 10：门同样要有证据，说不出被哪个真实事故或风险证明就不加，思路同 R5。
- 与 08、09、12：本篇负责这些检查的放置与编排，具体判定标准在各卡片。
- 与学习速度的张力：门太慢会拖垮反馈，提交前只放秒级检查，重检查放 CI 与发布前。
## 可执行的检查

| 检查项 | 执行位置 | 判定标准 |
| --- | --- | --- |
| 模块依赖方向与禁止直接引用 | 提交 / CI | 出现禁止方向的引用即失败 |
| 门登记完整性：来源、阈值、负责人、豁免到期日 | CI（登记表校验） | 字段缺失或豁免过期即告警 |
| 回滚演练：灰度回滚路径定期演练 | 发布 | 演练失败则不放量（演练周期按团队约定） |
| 灰度监控：崩溃率、错误率、关键业务指标 | 线上（灰度期） | 超过约定阈值自动回滚（阈值示例值，须按项目基线设定） |
| 复盘闭环：复盘单含「沉淀的自动化检查」字段 | 线上（事故后） | 无检查链接且无不可机检的说明，复盘不关闭 |
| 门健康度：命中、误报、耗时统计 | CI（定期任务） | 误报率或耗时超出团队约定则复核，长期零命中且无风险支撑则降级或删除 |

## 来源与扩展

- 来自原文《演进式架构与 YAGNI》：适应度函数是演进式架构的核心机制；在 CI 中校验依赖方向、做性能基准与 API 契约测试（Consumer-Driven Contracts）；简化代码时由适应度函数守住核心质量指标。
- 本文扩展：六类检查的分类、四个放置阶段、灰度与自动回滚、事故复盘闭环、质量门的成本与误报控制，以及全部示例。
- 需按实际版本核对：具体检查工具在 Cocos / TypeScript 工程中的选型按所用版本与工程选型核对；灰度放量比例、时长与回滚阈值按产品风险与实测设定；若产品涉及真实资金或受监管，灰度、回滚与日志留存要求按所在辖区核对。
