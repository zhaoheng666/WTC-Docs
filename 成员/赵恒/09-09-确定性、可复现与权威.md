# 09 确定性、可复现与权威

> 源自飞书文档 · 最后同步：2026-10-30

**一句话**：若产品涉及真实资金或受监管，Spin 的结果与账务只能由服务端产生并落账，客户端只负责表现；超时、断线后用回合 ID / 幂等号查询原回合，不重发新回合。

> 层级：L3 接缝 ｜ 对应痛点：配置或数值出错、线上事故；策划、美术、程序、服务端联调扯皮 ｜ 来源：本文扩展

## 为什么需要它

一次 Spin 同时涉及随机结果、资金和表现。客户端与服务端各算一份、断线后重发请求、线上问题无法复现，最终都会变成「账对不上，且无证据可查」的事故，也是联调扯皮的高发区。要先回答三件事：谁说了算，同一请求会不会结算两次，出了问题能否复现并对账。

## 核心主张

- 权威只有一个：若产品涉及真实资金或受监管，随机结果、赔付与账务只在服务端产生，客户端持有的是快照而不是真相。
- 幂等先于重试：任何会改变账务的请求都带幂等号，重复到达只结算一次，并返回首次结果。
- 回合是显式状态机：请求中、已结算、已确认、已展示，只允许前进；断线恢复靠查询未决回合，禁止重发新 Spin。
- 可复现是测试环境的能力：种子化随机数加请求回放用来复现问题，生产环境不接受客户端传入的种子。
- 三方可对：请求、结果、账务三份记录用同一回合 ID 串联，能自动对账。
## 怎么做

1. 划权威边界：在设计文档写明结算权威在服务端；客户端不做命中判定与金额运算，表现层只读快照（见 06）。这属于单向门，按 R4 写 ADR（见 01）。
1. 定回合标识：客户端按一次用户意图生成一个幂等号，服务端生成回合 ID 并与之绑定；两者写进协议契约（见 08）。
1. 定状态机：已结算指服务端账务落账；已确认指客户端回执已收到结果；已展示指表现完成回报，仅用于埋点与运营核对，不得反向影响账务。四态划分是本文建议，按实际协议调整。
1. 定恢复流程：超时或重连后先查询未决回合并按快照恢复表现，再开放下注。重试复用原幂等号；回合长期停在「请求中」时的处置规则由账务与运营规则决定。
1. 注入随机数源：结算只通过可注入的随机数接口取值；测试环境记录「种子 + 配置版本 + 输入序列」即可回放复现。
1. 写三联记录：每个回合记录请求、结果、账务，带同一回合 ID、配置版本与时间，定时自动对账。
1. 配置变更后模拟跑数：批量模拟，验证命中率与回报率在数学模型给定的容差内（见 05、11）。
```typescript
type RoundState = "pending" | "settled" | "confirmed" | "presented";

// 服务端：idemKey 需有唯一约束，查重与创建必须原子（示例，类型从略）
async function spin(req: SpinRequest, store: RoundStore, rng: Rng, ledger: Ledger) {
  const existed = await store.findByIdemKey(req.idemKey);
  if (existed) return existed;                      // 重发或重试：不再结算
  const round = await store.create({ idemKey: req.idemKey, state: "pending" });
  const result = settle(req.bet, rng);              // 随机数由服务端注入
  await ledger.apply(round.roundId, result.delta);  // 以回合 ID 幂等记账
  return store.advance(round.roundId, "settled", result);
}

// 客户端：进入机台先查未决回合，再允许新 Spin
async function recover(api: SpinApi) {
  const open = await api.queryOpenRounds();         // 已结算但未确认
  for (const r of open) {
    await present(r.snapshot);                      // 按快照恢复表现
    await api.confirm(r.roundId);
  }
}
```

## 在 Slots / Cocos 项目里的落地

| 场景 | 做法 | 反例 |
| --- | --- | --- |
| Spin 结算 | 服务端产出停轴结果与赔付，客户端按快照驱动转轴停位和动画 | 客户端本地算赢线再与服务端「校验」，不一致时各说各话 |
| 断线重连 | 进入机台后先查未决回合，用快照恢复表现，再开放下注按钮 | 重连后直接回到待机界面，用户看不到上一把结果 |
| 超时与连点 | 一次用户意图一个幂等号，回合未结束时锁定下注，重试复用原幂等号 | 超时后换新请求 ID 重发，造成重复扣注 |
| 问题复现 | 测试环境用种子化随机数并录制请求序列回放；日志带回合 ID 与配置版本 | 线上问题只靠截图和口述，正式包里留着改种子的调试开关 |
| 配置发布验收 | 配置变更触发批量模拟，命中率与回报率在容差内才放行 | 只核对表格字段，不跑数就发布 |

## 评审清单

| 评审类型 | 检查问句 | 不通过信号 |
| --- | --- | --- |
| 设计评审 | 结果与账务的权威方是否只有一个，并写明是服务端？ | 客户端与服务端都能产生结果，或写着「以客户端为准」 |
| 设计评审 | 请求是否带幂等号，重复请求的返回语义是否写进契约？ | 协议没有幂等字段，重试语义靠口头约定 |
| 设计评审 | 回合状态机是否列全状态、合法迁移与超时归属？ | 只有成功与失败两态，「请求中」超时无人负责 |
| 设计评审 | 断线与超时后的恢复路径是否是查询原回合？ | 恢复流程里出现「重新发起 Spin」 |
| 设计评审 | 能否用回合 ID 把请求、结果、账务三方对上，差异谁处理？ | 日志没有共同 ID，对账靠人工抽查 |
| 代码评审 | 客户端是否出现赔付、赢线的计算或结果字段的改写？ | 客户端代码里有金额运算，而不是读取快照 |
| 代码评审 | 随机数源是否可注入，生产环境是否拒绝客户端传种子？ | 业务代码直接调用全局随机函数，协议里有 seed 字段进入生产 |
| 代码评审 | 重试是否复用同一幂等号，状态迁移是否有重复请求用例？ | 重试处重新生成请求 ID，没有「同一幂等号发两次」的测试 |

## 误用与反模式

- 客户端先算先播、服务端事后校验：看似降低延迟，实质把权威交给了客户端，对不上时只能补偿。
- 超时后自动重发一个新 Spin：重复扣注的典型来源，恢复必须是查询。
- 把种子、调试开关或「强制结果」带进正式包：同时破坏确定性与权威。
- 把确定性理解为全部逻辑可回放：需要可复现的是结算链路与配置版本，表现层动画不必逐帧确定。
- 审计日志只记结果，不记请求与配置版本：出了争议无法还原当时的输入。
## 取舍与边界

- 不适用或可从轻：无资金的单机玩法与演示原型。社交 / 免费币类产品仍建议服务端权威以防篡改，合规要求通常更轻，以实际要求为准。
- 与 06：表现层只读快照、不持有权威状态，两者互为前提。与 05：数学模型是策略数据加结算机制，高危配置的模拟回归在本篇落地。
- 与 10：回放与对账先覆盖 Spin 这一条链路，不为所有玩法一次建成回放平台。
- 与 12：服务端权威会增加一次往返，用转动动画与预取遮掩等待，不用让客户端先出结果来换速度；按 R1，资金安全高于学习速度与结构整洁。
## 可执行的检查

| 检查项 | 执行位置 | 判定标准 |
| --- | --- | --- |
| 契约字段检查：请求含幂等号，响应含回合 ID 与状态 | CI | schema 缺字段或破坏兼容即失败（见 08） |
| 重复请求回放：同一幂等号发两次，并模拟断线后查询 | CI | 账务只有一条记录，两次返回的快照一致 |
| 客户端结算与种子入口扫描 | 提交 / CI | 客户端出现赔付运算，或生产协议带 seed 入口即失败（规则按项目命名约定定义） |
| 回放一致性：固定种子、配置版本与输入序列 | CI（测试环境） | 逐回合结果序列完全一致 |
| 模拟跑数：配置变更后批量模拟 | CI / 发布前 | 命中率与回报率落在数学模型给定的容差内，超差阻断发布 |
| 三方对账与未决回合监控 | 线上（定时） | 对账差异大于 0 即告警；滞留回合数超阈值告警（阈值示例值，须按实测与账务规则设定） |
