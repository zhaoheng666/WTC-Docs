# 06 实时层与元层分治

> 源自飞书文档 · 最后同步：2026-10-30

**一句话**：逐帧运行的实时表现层与事件驱动的元层是两类代码，要用不同手法设计：元层按 02 做领域建模，热路径追求数据扁平与对象复用；两层只经「命令与快照下行、事件回调上行」的窄接缝相连，表现层只读快照，不持有权威状态。

> 层级：L2 切分 ｜ 对应痛点：性能、包体、加载超标；需求频繁变更导致返工；技术债积压、不敢重构 ｜ 来源：本文扩展（与 02 领域建模、04 机制与策略分离一致）

## 为什么需要它

把领域对象图、事件总线和多层抽象带进每帧都跑的转轴与粒子，会拖慢帧时间并带来内存分配抖动；反过来，把大厅任务、VIP 规则写成界面组件里的逐帧轮询，规则散落、难改难测。两类代码的变化原因与性能约束不同，混在一起，性能问题和需求返工会互相放大。

## 核心主张

- 先分类再设计：问「这段代码每帧都执行吗」，是则按热路径设计，否则按元层设计。
- 02 的领域建模适用于元层，不要硬套到逐帧热路径；热路径关注数据扁平、对象复用、不在每帧分配与查找。
- 两层之间只有两条通道：下行是命令与只读快照，上行是事件回调；任何一层都不直接引用对方的内部对象。
- 表现层只读快照，不持有也不推导权威状态；结果由元层或服务端给出，表现层只负责演出（见 09）。
- ECS（实体组件系统）与数据导向是可选手段，不是必选：没有热点证据就不整体迁移（见规则 R5）。
## 怎么做

1. 给模块打层标签：每个模块登记「实时 / 元层」，并写明判别依据（是否逐帧、变化原因是画面还是规则）。
1. 元层按 02 建模：状态与规则放进领域模型，界面订阅状态变化，经命令驱动表现层。
1. 热路径守三条：数据扁平（预分配数组、数值 ID，少用字符串键查找）；对象复用（频繁出现的节点走对象池 NodePool，取用与归还成对）；update 内不分配、不查找（引用在 onLoad 或 start 阶段缓存）。
1. 定义接缝协议：下行 = 命令加不可变快照；上行 = 带回合 ID 的事件回调（停轮、演出结束、玩家点击）。
1. 让回调路径完整：正常播放、快速停轮、被中断（切后台）、断线恢复四条路径，演出结束事件都必须恰好到达一次，且处理可重入。
1. 给热路径设预算并度量：60fps 一帧约 16.7ms，30fps 约 33.3ms；各子系统的分摊值须按项目实测设定（见 12）。
```typescript
// 下行：元层 → 表现层（命令 + 只读快照）
interface SpinSnapshot {
  readonly roundId: string;
  readonly stops: readonly number[];    // 每轴停止位置，扁平数组
}
type PresentationCommand =
  | { kind: "playSpin"; snapshot: SpinSnapshot }
  | { kind: "skipToResult"; roundId: string };

// 上行：表现层 → 元层（事件回调，带回合 ID，处理须幂等）
interface PresentationEvents {
  onReelsStopped(roundId: string): void;
  onPresentationDone(roundId: string): void;
}

// 热路径：在 onLoad 预分配；update 内不创建对象、不按名字查找
class ReelDriver {
  private offsets = new Float32Array(5);   // 示例：5 轴
  private speed = 0;                       // 示例：由快照与命令设置
  update(dt: number): void {
    for (let i = 0; i < this.offsets.length; i++) this.offsets[i] += this.speed * dt;
  }
}
```

## 在 Slots / Cocos 项目里的落地

| 场景 | 做法 | 反例 |
| --- | --- | --- |
| 转轴滚动与停轮 | 热路径：预分配与扁平数组，读 SpinSnapshot 决定停轮位置；转轴驱动是机制，卷轴带与赔付是策略数据（见 04、05） | update 里每帧遍历节点树按名字找子节点、创建临时对象 |
| 赢线特效、粒子、飘字 | 预制体（Prefab）实例化一次，经 NodePool 取用与归还；归还时重置状态 | 每次中奖实例化再销毁，累积后触发卡顿 |
| 大厅、任务、VIP、商店 | 元层：领域模型加事件驱动，界面订阅状态；规则在模型里（见 02） | 在某个面板组件的 update 里轮询任务进度 |
| 结果与余额 | 表现层读快照演出，不改余额、不决定输赢（见 09） | 动画播完才在客户端「算」赢多少 |
| 快速停轮、跳过动画 | 发 skipToResult 命令直达终态，仍回调 onPresentationDone | 跳过动画导致回调丢失，回合状态卡住 |

## 评审清单

| 评审类型 | 检查问句 | 不通过信号 |
| --- | --- | --- |
| 设计评审 | 每个模块是否标明属于实时层还是元层，并有判别依据？ | 同一模块既逐帧演出又承载业务规则 |
| 设计评审 | 两层之间是否只有命令、快照下行与事件回调上行？ | 表现层直接引用领域对象，或元层持有动画节点 |
| 设计评审 | 热路径是否有帧预算与度量方式（见 12）？ | 只写「保证流畅」，没有数字与机型分档 |
| 设计评审 | 表现层是否持有或推导权威状态？ | 表现层存余额、局状态并作为后续逻辑依据 |
| 设计评审 | 跳过、切后台、断线恢复时，演出结束回调是否仍到达？ | 回调只在正常播放路径上触发 |
| 代码评审 | update 内是否出现对象创建、闭包创建、字符串拼接、按名查找？ | 每帧产生临时对象，或每帧遍历查找 |
| 代码评审 | 频繁出现的节点是否走对象池且取用与归还成对？ | 只取不还，或归还时不重置状态 |
| 代码评审 | 元层代码是否引用了动画、节点类型？ | 领域模型里出现节点或特效类型 |
| 代码评审 | 事件回调是否带回合 ID 并能容忍重复触发？ | 重复回调导致重复结算或重复发奖 |

## 误用与反模式

- 把 02 的实体、聚合、事件总线整套搬进逐帧路径：每帧生成事件与对象，帧时间和内存分配一起抖动。
- 为「统一」而统一：用同一套事件总线驱动逐帧动画与大厅规则，两类约束互相迁就。
- 没有热点证据就整体改造成严格 ECS：成本大，收益说不出被哪个真实瓶颈证明（规则 R5）。
- 表现层偷偷存状态：在动画回调里改余额、回合状态，断线恢复时与权威结果不一致。
- 对象池只取不还，或归还不重置，残留上一局的特效与状态。
## 取舍与边界

- 不用或不必强求：表现层很薄（静态面板、纯展示页）时，不需要刻意造一层接缝；出现第二类真实的热路径需求再拆（规则 R2）。
- 与 02：02 管元层的领域边界，本卡划定它的适用范围，不推翻它。
- 与 03、04：转轴驱动等机制由内核提供，两层接缝是内核对机台组件的接口形态之一；快照里是策略数据的运行结果。
- 与 07：外部服务适配放在元层一侧；热路径内不要为「抽象整洁」多加间接层。
- 与 09：表现层不持有权威状态是硬边界。
- 裁决：整洁与帧时间冲突时，表现层内部可以局部牺牲整洁（排序上结构整洁最低，规则 R1），但接缝与权威状态边界不让步；若产品涉及真实资金或受监管，该边界关系到结算正确性，优先级更高。
## 可执行的检查

| 检查项 | 执行位置 | 判定标准 |
| --- | --- | --- |
| 依赖方向检查：元层不得引用表现层与节点类型，表现层不得引用领域模型 | 提交 / CI | 违规引用数为 0 |
| 热路径静态规则：update 函数内禁止对象创建、正则、字符串拼接 | 提交 / CI | 命中且无登记豁免则失败 |
| 帧时间基准：典型转轴加中奖特效场景，按目标机型分档采样 | CI / 发布 | 超出登记预算（示例值，须按项目实测设定）则失败 |
| 对象池对账：一局结束后借出未还数量 | CI | 借出未还数量大于 0 则失败 |
| 回调完整性测试：正常、跳过、中断、断线恢复四条路径 | CI | 任一路径演出结束回调次数不等于 1 则失败 |
| 卡顿帧占比与内存趋势告警 | 线上 | 超出项目设定阈值则告警 |
