# 10 演进式架构与 YAGNI

> 源自飞书文档 · 最后同步：2026-10-30

**一句话**：YAGNI 管范围（不做未被证实的功能与抽象），演进式架构管变更成本（用边界与安全网让将来改得动）；抽象只在有真实变化证明时才长出来（见规则 R2、R5）。

> 层级：L4 演进与守护 ｜ 对应痛点：需求频繁变更导致返工；技术债积压、不敢重构；多项目或多款游戏复用困难 ｜ 来源：原文《演进式架构（Evolutionary Architecture）与 YAGNI 原则》

## 为什么需要它

需求变化快时，团队容易两头犯错：一头把「以后可能需要」都做成扩展点，代码膨胀，真正的变化来了反而改不动；另一头以简单为由省略必要边界，机台代码长成一团，技术债积压、没人敢重构。需要一条可判定的线：什么现在做，什么先登记，什么靠安全网保护。

## 核心主张

- YAGNI 管范围，演进式架构管变更成本：前者拒绝未被证实的复杂度，后者保证将来变更低成本、无破坏。
- 先做模块化单体加清晰边界：客户端用单工程多模块、多 Asset Bundle，不预先拆成多工程或多服务。
- 抽象沿阶梯上升，每一级都要有证据：复制、第三次重复、抽取、第二个真实实现、稳定契约（R2、R5）。
- 底线靠适应度函数（Fitness Function，可自动执行的架构 / 质量底线检查，见 11）守住，不靠口头约定。
- 「以后可能需要」登记成待办并写明触发条件，不写进代码；决策推迟到最晚责任时刻，但单向门不能拖过头（R4）。
## 怎么做

1. 只为已确认的变化轴留边界：本季度确定会发生的变化（新机台、新活动、新渠道）才预留，其余不预留。
1. 按变化原因划模块，而不是按技术层：模块间只经少量显式接口通信（见 03、07）。
1. 走阶梯：前两次相似需求直接复制；第三次重复才抽取，先抽到模块内部；出现第二个真实实现才引入端口；跨团队、跨进程或跨版本才冻结契约（R2、R3）。
1. 动手前先建安全网：遗留代码先补特征化测试（Characterization Test，把现有行为原样记成基线）和回放对账，再重构；没有安全网的重构按高风险处理。
1. 老机台用绞杀者（Strangler）方式：新旧并行，按模块或机台逐步切换，旧实现无引用后下线，不做一次性重写。
1. 「以后可能需要」只登记，触发条件成真才进入阶梯；登记项到期复核，仍无触发就删除。
1. 单向门类决策（协议字段语义、账务数据结构等，见 01）要在最晚责任时刻前用原型验证，并写 ADR。
```yaml
# 「以后可能需要」登记示例：只写触发条件，不写代码
- idea: 机台支持多语言文案热切换
  trigger: 出现第二个明确要求该能力的渠道包
  evidence_needed: 第三次出现同类渠道分支，或第二个真实使用方
  owner: 机台组接口人
  review_by: 季度末复核   # 到期仍无触发则删除
```

## 在 Slots / Cocos 项目里的落地

| 场景 | 做法 | 反例 |
| --- | --- | --- |
| 第二款机台立项 | 先复制第一款中需要的部分，两份各自可运行；对比后只抽取真正相同的部分 | 立项前先设计通用机台框架，为想象中的第三、四款预留扩展点 |
| 客户端工程组织 | 单工程多模块，按机台用 Asset Bundle 分包，边界由依赖检查守住（见 03、11） | 一开始拆成多个工程仓库，或所有代码混在一个目录里没有边界 |
| 渠道差异 | 第一个渠道直接写；出现第二个真实渠道再引入端口与适配器（见 07） | 只有一个渠道就写全套渠道抽象层，或在业务代码里散落渠道判断 |
| 老机台重构 | 先补特征化测试与回放对账，再按模块用绞杀者方式替换 | 没有基线就大改，或停下业务做一次性重写 |
| 新活动玩法 | 登记触发条件；条件成真后先用配置表达差异，不够再请内核支持（见 04、05） | 为尚未立项的活动预先做通用活动引擎 |

## 评审清单

| 评审类型 | 检查问句 | 不通过信号 |
| --- | --- | --- |
| 设计评审 | 这个抽象或扩展点被哪个已发生的真实变化证明？（R5） | 回答是「以后可能」「万一」 |
| 设计评审 | 是否已有第三次重复或第二个真实实现，才引入抽取、端口或内核？（R2） | 只有一个实现就先写接口层；同类复制超过三处仍无抽取计划 |
| 设计评审 | 边界是否按变化原因划分，模块间是否只经显式接口依赖？ | 边界按技术层划分，或以简单为由完全没有模块边界 |
| 设计评审 | 重构或重写方案是否有安全网和分步回退路径？ | 没有基线测试与回放，方案是一次性切换 |
| 代码评审 | 新增的接口、配置项、扩展点是否至少有一个当前调用方？ | 无调用方的导出符号、未使用的参数与配置项 |
| 代码评审 | 是否出现跨模块直接引用或绕过公开接口？ | 引用对方内部文件；依赖检查被加白名单且无说明 |
| 代码评审 | 「先复制」的重复代码是否标注了触发抽取的条件？ | 复制后无标记，三处以上才被发现 |

## 误用与反模式

- 把「演进式架构」理解为不需要设计（原文误区一）：它要求更强的解耦能力和边界感知，知道在哪里留演进缝隙。
- 把 YAGNI 理解为只写烂代码（原文误区二）：YAGNI 拒绝未被证实的复杂功能，不拒绝清晰命名、单一职责和可测试性。
- 把「以后可能需要」都做成扩展点，或以简单为由省略必要边界（根文档对照表的误用）。
- 第一次重复就抽取：抽象被两个场景的偶然相似绑死，之后每次都靠加参数打补丁。
- 拿 YAGNI 当拒绝一切前置设计的理由：不可逆决策与资金、合规相关边界不适用，按 R1 要前置设计。
## 取舍与边界

- 不适用 YAGNI 的情形：单向门决策（协议字段语义、账务数据结构、结算权威边界，见 01、09）。按 R1 风险优先，这些边界要前置设计并留 ADR。
- 与 03：R2 规定 2~3 个真实扩展方才立内核，本篇给通用阶梯，03 给内核的具体要求。
- 与 08：契约冻结按 R3，单人单模块内不冻结，一旦跨团队立刻冻结。
- 与 11：演进以适应度函数为前提；没有机检的「清晰边界」会在迭代中悄悄退化（R6）。
- 与 12：性能与包体底线属于适应度函数，不适用「先不管，以后再说」。
## 可执行的检查

| 检查项 | 执行位置 | 判定标准 |
| --- | --- | --- |
| 模块依赖方向与跨模块引用检查 | 提交 / CI | 出现禁止方向的引用或绕过公开接口即失败（规则按项目模块划分定义） |
| 抽象举证：合并请求说明新增接口对应的真实变化 | 提交（合并请求模板） | 说明缺失或无当前调用方则不通过 |
| 未引用的导出符号与配置项扫描 | CI | 列入告警清单，按季度清理（清理周期为示例，按团队约定） |
| 待办登记到期复核 | CI（定期任务） | 超过复核日期未处理自动提醒，仍无触发则删除 |
| 重构前基线：特征化测试与回放对账 | 提交 / CI | 基线不通过，重构不得合入 |

- 本文扩展：抽象成熟度阶梯与 R2 的对应；单工程多模块、多 bundle 的客户端落地；技术债与「不敢重构」的安全网、绞杀者做法；待办登记格式；全部表格与示例。
