# 01 约束先行与可逆性分级

> 源自飞书文档 · 最后同步：2026-10-30

**一句话**：设计的第一步是列约束、给每个决策分级，而不是选架构。单向门决定在最晚责任时刻前用原型验证并留 ADR，双向门决定当场做、不开会。

> 层级：L1 价值与约束 ｜ 对应痛点：需求频繁变更导致返工；技术债积压、不敢重构 ｜ 来源：本文扩展（呼应原文《演进式架构与 YAGNI 原则》的最晚责任时刻）

## 为什么需要它

代价最高的返工，往往来自「决定得太早且改不回去」：协议字段语义、账务数据结构一旦上线，就带着历史数据，改一次等于一次迁移加一轮事故；而 UI 结构、动画实现改错了，只是重写几天。不列约束、不分级，团队就会用同一种力度对待所有决定，要么对双向门过度评审拖慢速度，要么对单向门草率拍板留下返工和技术债。

## 核心主张

- 约束是设计的输入：任何架构方案都要能说出自己满足了哪几条约束，说不出就不进评审。
- 决策按可逆性分三档，每档有固定的节奏和材料，分级在评审前完成，不在会上争。
- 单向门要晚做、做足证据：在最晚责任时刻（Last Responsible Moment）前用原型验证，决定后写 ADR（Architecture Decision Record，决策日志）并留证据（R4）。
- 先打通一条完整的 Spin 垂直切片（Vertical Slice），再横向扩展：风险最大的接缝最先暴露（R1）。
- 需求变更先归类再动手，返工必须归因到「需求变化 / 理解偏差 / 边界划错」之一。
## 怎么做

1. 列约束。一页写完，每条标注「是否可协商」和「怎么校验」。
| 约束维度 | 要写下什么 | 锁定信号 |
| --- | --- | --- |
| 合规与认证 | 适用的合规与认证范围、送审节点 | 若产品涉及真实资金或受监管，结果与账务只能由服务端产生（见 09） |
| 数学模型与 RTP | RTP（Return To Player，理论返还率）由谁定、何时锁定、锁定后谁能改 | 锁定后任何数据变更都要重新模拟回归（见 05） |
| 平台审核与包体限制 | 目标平台的包体上限与审核要点 | 数值为示例值，须按平台当前要求与项目实测设定（见 12） |
| 目标机型性能 | 机型分档、帧率目标、内存上限 | 60fps 约 16.7ms，30fps 约 33.3ms |
| 上线周期 | 里程碑、送审与热更窗口 | 窗口不可移动时，范围必须可裁剪 |
| 团队规模与分工 | 小组数、接口人、谁能独立交付 | 跨组的决定默认升档（见 14） |

1. 给决策分级。对每个待定决定问三句：上线后能否不迁移数据就改回去？是否触及协议语义、账务、结算权威、存档或对外数据格式？回退成本是否超过一个迭代？任一答案指向「改不回去」就升一档（R1：不可逆高于学习速度）。
| 档位 | 典型决定 | 节奏 | 所需材料 |
| --- | --- | --- | --- |
| 单向门 | 协议字段语义、账务数据结构、结算权威边界、存档与对外数据格式 | 慢：最晚责任时刻前定，跨团队评审 | 原型验证结果、兼容与迁移方案、ADR、证据 |
| 中间档 | 配置 schema、资源规范 | 中：评审后版本化，允许带迁移的演进 | schema 草案、兼容策略、校验器 |
| 双向门 | UI 结构、动画实现、模块内部划分 | 快：负责人当场决定，事后可改 | 一句话记录假设 |

1. 单向门走原型：在最晚责任时刻（再拖就会产生实质损失的节点）前，用原型验证最危险的假设，决定后立即写 ADR，模板见附录二。
1. 先做垂直切片：打通客户端 → 服务端 → 结算 → 表现 → 埋点五段，每段先用最简实现，验收标准是整条链路可回放、可对账。
1. 变更先分类：变的是策略，改配置，见 04；变的是机制，改内核，见 03；变的是领域概念，改模型，见 02。
1. 返工必须归因：需求变化（外部确实变了）要降低变更成本；理解偏差要契约先行（见 08）；边界划错要重切模块（见 02）。
```yaml
# 决策分级登记（示例）
- decision: Spin 响应中 win 字段的语义
  gate: one-way               # one-way / middle / two-way
  reason: 已发布客户端与账务对账都依赖该字段
  last_responsible_moment: 第一个跨端联调版本之前
  evidence: [原型联调记录, 兼容测试结果]
  adr: ADR-示例-001
- decision: 停轴动画的实现方式
  gate: two-way
  reason: 模块内部实现，可随时替换
  owner: 机台组负责人
```

## 在 Slots / Cocos 项目里的落地

| 场景 | 做法 | 反例 |
| --- | --- | --- |
| 某款 Slots 机台立项 | 立项当天出约束清单与分级表，第一个里程碑就是 Spin 切片 | 先搭完整框架和全部玩法壳，联调时才发现协议语义对不上 |
| Spin 协议字段 | 单向门：原型联调加兼容测试，定后写 ADR，变更走契约流程（见 08） | 客户端按猜测实现、服务端按另一种理解返回，上线后靠补丁兼容 |
| 配置 schema 与资源规范 | 中间档：评审后版本化，附校验器（见 05、13） | 每款机台各自约定，换机台时才发现互不兼容 |
| UI 层级、Prefab 内部结构 | 双向门：负责人当场定，后续可重构 | 为 UI 结构召集跨组评审、写长文档 |
| 某次需求变更：新增一档赔付 | 先判定属于改策略（改配置），不动内核 | 默认当作改代码，排进下个版本 |

## 评审清单

| 评审类型 | 检查问句 | 不通过信号 |
| --- | --- | --- |
| 设计评审 | 约束清单是否覆盖六个维度，且每条标注了可否协商与校验方式？ | 只有「性能要好」「尽快上线」这类无法判定的表述 |
| 设计评审 | 每个待定决定是否标了档位并给出依据（三问）？ | 所有决定一视同仁，或档位没有依据 |
| 设计评审 | 每个单向门是否有原型验证结果、ADR 和最晚责任时刻？ | 单向门靠口头同意，或「以后再说」没有期限 |
| 设计评审 | 方案是否包含 Spin 垂直切片及其验收标准？ | 里程碑按模块排期，联调排在最后 |
| 代码评审 | 改协议字段语义、账务数据结构、存档格式的 PR，是否关联 ADR 或契约变更单？ | 直接改字段含义，没有关联记录 |
| 代码评审 | 本次改动属于改策略、改机制、改领域哪一类，是否落在对应位置？ | 用改代码处理本可改配置的变更，或机制里出现活动判断 |
| 代码评审 | 双向门级改动是否未被额外流程阻塞？ | 模块内部重构要求跨组会签，说明分级失效 |

## 误用与反模式

- 约束清单写成愿望清单：无法校验的约束等于没有。
- 所有决定都当单向门：评审会泛滥，团队学会绕过流程。
- 所有决定都当双向门：以「以后再改」为由跳过协议与账务的原型，线上有了数据才发现改不动。
- 垂直切片做成一次性演示后推倒重写：协议、结算、埋点这几个接缝要按生产标准保留。
- 分级一次定死：双向门会随数据积累变成单向门（例如 UI 临时字段被写进存档），里程碑要复核档位。
## 取舍与边界

- 单人单模块的原型期不必做完整分级（R3：单人单模块内不冻结），但要记下「哪些决定一旦进入存档或协议就变成单向门」。
- 与 10（YAGNI 与延迟决策）的张力：延迟决定不等于不验证。按 R4，推迟到最晚责任时刻，但在此之前用原型验证。
- 与 R1 的裁决：学习速度与不可逆、合规、资金安全冲突时，后者优先，单向门宁可多花一周做原型。
- 与 04 的张力：把策略做成配置能把改代码降成改数据，但配置 schema 本身是中间档，要版本化（见 05）。
## 可执行的检查

| 检查项 | 执行位置 | 判定标准 |
| --- | --- | --- |
| 决策分级表完整性 | 提交（设计文档合入前） | 每个标「单向门」的条目有 ADR 编号、最晚责任时刻、证据列表，缺一不通过 |
| 单向门文件改动拦截 | CI | 修改协议 schema、账务数据结构定义、存档格式的 PR 必须带 ADR 或契约变更单编号，否则失败 |
| Spin 切片冒烟 | CI / 发布 | 请求、结算、表现、埋点端到端用例每次构建运行，任一环节缺失或失败即阻断发布 |
| 档位复核 | 发布（里程碑） | 每个里程碑复核登记表，升档的条目有记录和新增材料 |
| 返工根因登记 | 线上（迭代复盘） | 每次返工关闭时必须选「需求变化 / 理解偏差 / 边界划错」之一，缺项不能关闭 |

## 来源与扩展

- 来自原文：《演进式架构与 YAGNI 原则》中的延迟决策（最晚责任时刻）。其余内容为本文扩展，包括约束清单维度、三档划分及节奏、垂直切片、变更分类与返工归因。
- 单向门 / 双向门是业界通用说法，本文按 R4 固定用法。
- 需按实际版本 / 辖区核对：合规与认证要求（若涉及真实资金或受监管，按所在辖区与认证机构核对；社交 / 免费币类通常更轻，以实际要求为准）；RTP 锁定时机与变更流程（按产品与认证要求核对）；平台审核与包体限制（按目标平台当前要求核对，数值均为示例值，须按项目实测设定）；Asset Bundle 划分的可逆性取决于热更与发布方式（按所用引擎版本与发布方式核对）。
