# 12 性能与资源预算

> 源自飞书文档 · 最后同步：2026-10-30

**一句话**：性能、包体与加载时长要先定预算、再分摊到各子系统、由 CI 度量并设门；超预算走「审批例外加限期偿还」，不留到临近发布才处理。

> 层级：L4 演进与守护 ｜ 对应痛点：性能、包体、加载超标 ｜ 来源：本文扩展

## 为什么需要它

Slots 机台的动画、粒子、音频和字体只增不减，包体、内存和帧时间往往临近发布才超标，此时没人说得清是谁超的、该砍谁。预算先行把总量拆成各子系统的份额，超标时能定位到责任方，也有明确的偿还路径。

## 核心主张

- 预算先行：目标机型分档、帧率目标、内存上限、首包体积、首屏与加载时长在立项时就定，数字一律按项目实测设定。
- 预算要分摊：总额拆到子系统和机台，每份预算有负责人；没有归属的预算等于没有预算。
- 首包最小化、机台按需加载：首包只放平台内核与大厅，机台资源按机台分包。
- 先测量再优化：测量、定位、修改、回归，不凭感觉动手。
- 超预算有流程：谁批准例外、期限多长、如何偿还，都要留记录。
## 怎么做

1. 机型分档：按实际用户设备统计分为若干档，每档定帧率目标；60fps 对应约 16.7ms，30fps 对应约 33.3ms 每帧。
1. 定预算总表：每档一行，含帧时间、内存上限、首包体积、首屏与加载时长；所有数值都是示例值，须按项目实测设定。
1. 分摊：帧时间分给逻辑、渲染、动画与粒子、音频；内存与体积分给首包、各机台分包、公共资源；每项写明负责人。
1. 定资源预算规则：纹理（尺寸上限、压缩格式、是否进图集）、骨骼动画与粒子（数量与同屏上限）、音频（时长、码率、格式）、字体（字符集裁剪）；规则写成资源规范检查，由提交钩子与 CI 执行（见 13）。
1. 分包与按需加载：首包只含内核与大厅；每款机台一个 Asset Bundle，进入机台时再加载；中奖特效、金币等高频节点用对象池（NodePool）复用，避免反复创建销毁；热更范围与版本对齐见 13。
1. 度量：分机型采样（以真机为准）、CI 基准、每次构建生成包体报表、趋势告警，基线随版本存档。
1. 超预算：登记例外，写明批准人、原因、偿还方案和期限；到期不还，同类新增一律阻断。
```yaml
# 预算总表与例外登记示例（全部取值为示例，须按项目实测设定）
tiers:
  low:
    frame_ms: 33.3          # 30fps 约 33.3ms
    memory_mb: "<按实测>"
    first_pack_mb: "<按实测>"
    load_s: "<按实测>"
  high:
    frame_ms: 16.7          # 60fps 约 16.7ms
exception:
  item: 某机台分包超出预算
  approver: 平台组负责人
  repay_by: 版本号或日期
  plan: 压缩纹理、裁剪字体、拆分分包
```

## 在 Slots / Cocos 项目里的落地

| 场景 | 做法 | 反例 |
| --- | --- | --- |
| 首包与分包 | 首包只放内核与大厅，每款机台一个分包，进入机台时按需加载 | 所有机台资源打进首包，或把每个小资源机械拆包造成请求碎片 |
| 纹理与图集 | 资源规范检查限制尺寸与压缩格式，同屏常用图合并图集 | 美术随手导出大尺寸原图，上线前才人工压缩 |
| 动画与粒子 | 给中奖大特效划定帧时间份额和同屏数量上限，高频节点用 NodePool | 特效只在高端机测试，低档机卡顿到线上才发现 |
| 加载时长 | 机台加载拆成「可玩前必需」和「后台预载」，进度页只等必需部分 | 一次性加载整个机台全部资源再显示画面 |
| 多机型验证 | 每档至少一台真机做采样基线，CI 跑基准并保存趋势 | 只在开发机或模拟器上看帧率 |

## 评审清单

| 评审类型 | 检查问句 | 不通过信号 |
| --- | --- | --- |
| 设计评审 | 是否有按机型分档的预算总表，并标明数值来源是实测？ | 预算只有「流畅」「尽量小」的描述 |
| 设计评审 | 预算是否已分摊到子系统和机台，并有负责人？ | 只有总预算，超了没人认领 |
| 设计评审 | 首包内容是否限于内核与大厅，机台资源是否按机台分包？ | 机台资源进首包，或细碎拆包没有依据 |
| 设计评审 | 超预算的例外流程（批准人、期限、偿还）是否定义？ | 流程是「先上线再说」 |
| 代码评审 | 新增资源是否符合资源预算规则（尺寸、格式、图集、字符集）？ | 未压缩的大图、整套字体未裁剪 |
| 代码评审 | 高频创建销毁的节点是否用对象池，逐帧路径是否避免分配与查找？ | update 内创建对象、每帧反复查询节点 |
| 代码评审 | 性能优化是否附测量前后的数据与回归基准？ | 只有「感觉更快了」，没有数据 |

## 误用与反模式

- 先做完再优化：临近发布才测，只剩砍内容和降画质可选。
- 只看平均值或只看高端机：低档机和卡顿的尾部才是用户真正遇到的问题。
- 预算只有一个总数：没有分摊就无法定位责任。
- 预算写成一次性文档：不进 CI、不随版本更新，几个版本后就失效。
- 例外永不偿还：例外变成常态，等于取消预算。
## 取舍与边界

- 原型与验证阶段预算可以放宽，但要记录当时的基线，不能完全不测；放宽属于可逆决定，快做即可（R4）。
- 与 06：热路径优化（数据扁平、对象池、避免每帧分配与查找）是预算在实时层的落地，元层更关心包体与加载。
- 与 10：不为「可能的低端机」提前做复杂优化，按预算与实测触发；但帧时间与包体底线属于适应度函数，不适用「先不管」（见 11、R6）。
- 与 09：服务端权威带来的往返延迟要计入 Spin 响应与加载预算，不用让客户端先出结果来换速度（R1）。
- 与 03：机械拆包会拖慢加载，分包粒度按机台而不是按资源。
## 可执行的检查

| 检查项 | 执行位置 | 判定标准 |
| --- | --- | --- |
| 包体报表与预算比对：首包与各分包体积 | CI / 发布 | 超过预算表上限即阻断，例外需审批登记 |
| 资源规范检查：纹理尺寸、压缩格式、图集、字符集、音频格式 | 提交 / CI | 不符合规则的资源不得合入（规则取值为示例，按项目设定） |
| 性能基准：分档基准场景的帧时间与内存 | CI / 发布 | 相对基线劣化超过约定比例告警，超过预算上限阻断（比例为示例值） |
| 趋势告警：包体、帧时间、内存按版本的趋势 | CI | 连续多个版本增长则告警 |
| 线上采样：分机型的帧率、内存、加载时长 | 线上 | 某档机型超预算的比例超过约定阈值则告警，并进入偿还流程 |
| 例外到期扫描 | CI（定期任务） | 超过偿还期限未处理则升级，并阻断同类新增 |
