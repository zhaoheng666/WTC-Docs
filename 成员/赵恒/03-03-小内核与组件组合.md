# 03 小内核与组件组合

> 源自飞书文档 · 最后同步：2026-10-30

**一句话**：内核只放不随业务变的机制（生命周期、通信管道、组件协议、故障隔离），所有会变的玩法、表现与外部依赖都做成组件；组件之间禁止直接 import，只经内核沟通。内核要小，但必须是生产级的。

> 层级：L2 切分 ｜ 对应痛点：多项目或多款游戏复用困难；需求频繁变更导致返工；技术债积压、不敢重构 ｜ 来源：原文《小内核与组件组合》 + 本文扩展

## 为什么需要它

多款机台之间复制粘贴，修一个缺陷要改 N 份；换个思路把共性堆进平台，平台里又长满 `if (machineId === ...)`，每上一款机台都要动平台。小内核把「不变的机制」与「变化的能力」切开：新增机台是新增组件，而不是修改平台。

## 核心主张

- 内核只管机制：生命周期编排、通信管道、组件协议、故障隔离；出现机台名、玩法规则或活动判断的代码，不属于内核。
- 变化的放组件，组件之间禁止直接 import，只能经内核的事件、依赖注入（DI）或扩展点沟通。
- 小是指职责少，不是实现粗糙：内核一旦出错就是全局事故，必须满足生产级的最低要求。
- 立内核的时机由 R2 裁决：第三款机台前先复制再抽取，出现 2~3 个真实扩展方才立内核。
- 组件边界与分包边界对齐，但不为每个资源单独拆包。
## 怎么做

1. 先复制，后抽取。前两款机台各自实现，复制可以接受；第三款开工前对比前两款：相同的机制抽成通用组件，不同的留在机台。每个抽取点要说得出被哪个真实变化证明（R5）。
1. 分三层，各有维护者：
| 层 | 管什么 | 不管什么 |
| --- | --- | --- |
| 小内核 | 生命周期编排、通信管道（事件与命令）、组件协议、故障隔离 | 任何玩法规则、机台差异、外部 SDK |
| 通用组件 | 转轴驱动、资源加载、音频、网络等跨机台共用能力（机制，见 04） | 具体机台的赔付表、活动规则 |
| 机台组件 | 特性玩法、主题表现，以及注入通用组件的机台策略数据 | 其他机台的实现细节 |

1. 定组件协议：名称、版本、依赖声明（`requires`）、`setup(ctx)`、`teardown()`。组件只通过 `ctx` 访问内核能力。
1. 三种沟通方式，不得绕开：事件（广播，监听者可有多个）、命令（有且只有一个处理者）、依赖注入（按接口取服务）。事件名与命令签名一旦跨团队使用，就是契约（见 08）。
1. 对齐引擎：组件逻辑落在 Component 脚本，可视部分放 Prefab，一个机台的脚本、Prefab 与资源作为一个 Asset Bundle，是起点而不是铁律。内核的 `setup`、`teardown` 与节点生命周期（onLoad、onEnable、onDisable、onDestroy）怎么对应，按所用版本核对。
1. 按下表落实生产级内核的最低要求。
| 最低要求 | 防住的问题 | 验证用例 |
| --- | --- | --- |
| 先 `setup` 成功再登记，失败则回滚已注册的命令与监听 | 先登记后 setup 导致半注册 | `setup` 抛错后，命令表与监听表无该组件残留 |
| 事件派发对每个监听器隔离异常，并上报组件名 | 一个监听器抛错使后续监听器都不执行 | 两个监听器，首个抛错，第二个仍被调用 |
| 命令与组件重名直接报错，需覆盖时显式声明并记录日志 | 静默覆盖或静默忽略，行为不可预期 | 重复注册同名命令，抛出明确错误 |
| 提供 `shutdown`，按依赖逆序调用 `teardown` | `teardown` 定义了却从未被调用 | 关闭后全部 `teardown` 被调用且顺序正确 |
| 依赖声明与拓扑排序，缺失或循环依赖启动即失败 | 加载顺序靠运气 | 缺失依赖与循环依赖各一例，启动阶段即报错 |
| 监听与命令按组件登记，卸载时统一清理 | 卸载后监听仍被触发，内存泄漏 | 卸载组件后，该组件的监听数为 0 |
| 组件声明所需内核版本，不兼容则拒绝加载 | 升级内核后组件行为悄悄变化 | 用低于要求的内核版本加载，得到明确的拒绝信息 |

```typescript
export interface Component {
  name: string;
  version: string;
  requires?: string[];                 // 依赖声明：内核据此排序，缺失即失败
  setup(ctx: ComponentContext): void | Promise<void>;
  teardown?(): void | Promise<void>;   // 由内核在 shutdown 时调用
}
class Kernel {
  private done = new Map<string, Component>();
  async use(c: Component) {
    if (this.done.has(c.name)) throw new Error(`重复组件: ${c.name}`);
    const ctx = this.createContext(c.name);  // 记录该组件的命令与监听
    try {
      await c.setup(ctx);
      this.done.set(c.name, c);              // setup 成功后才登记
    } catch (e) { ctx.dispose(); throw e; }  // 回滚，不留半注册
  }
  async shutdown() {                         // use 已按 requires 排序，逆序卸载
    for (const c of [...this.done.values()].reverse()) {
      try { await c.teardown?.(); } catch (e) { this.report(c.name, e); }
      this.disposeContext(c.name);
    }
  }
}
// 省略：emit 的逐监听器 try/catch、命令表的重名检测、依赖排序与版本校验
```

## 在 Slots / Cocos 项目里的落地

| 场景 | 做法 | 反例 |
| --- | --- | --- |
| 多款机台共用转轴驱动 | 转轴驱动做成通用组件，机台只提供卷轴带数据（策略，见 04） | 每款复制一份转轴脚本；或平台代码里按机台 ID 分支 |
| 机台的差异化特性玩法 | 一个特性一个 Component，经内核事件接收 Spin 结果，Prefab 负责表现 | 特性脚本直接 import 另一个机台的脚本或到处取节点 |
| 分包 | 一个机台的脚本、Prefab、资源归一个 Asset Bundle；通用组件放基础部分（按所用版本与发布方式核对） | 每个音效、每张图单独成包；或所有机台塞一个包，改一款全量更新 |
| 复用时机 | 第三款机台前先复制，抽取时登记被哪些机台的哪些变化证明 | 第一款机台就设计「通用机台框架」，预留十几个扩展点 |
| 内核新增能力 | 新增 API 需 2~3 个真实使用方，并带契约测试 | 为某一次活动在内核里加 `if (activityId)` |

## 评审清单

| 评审类型 | 检查问句 | 不通过信号 |
| --- | --- | --- |
| 设计评审 | 内核职责是否限于生命周期、通信、协议、故障隔离，新增职责是否有 2~3 个真实使用方？ | 出现玩法、机台、活动词汇；只有一个使用方就进内核 |
| 设计评审 | 抽取内核前是否已有第三款机台或 2~3 个真实扩展方（R2、R5）？ | 只有一款机台就先设计框架 |
| 设计评审 | 组件依赖图是否无环，依赖是否都在 `requires` 中声明？ | 组件知道其他组件的内部类；依赖靠加载顺序碰运气 |
| 设计评审 | 分包边界是否与组件边界对齐，没有按资源粒度机械拆包？ | 包数量随资源数增长；一个包内含多款机台 |
| 代码评审 | 组件文件是否引用了其他组件的实现（而非契约类型）？ | `import` 了其他机台或其他组件的脚本 |
| 代码评审 | `setup` 中登记的监听与命令，卸载时是否都被清理？ | 切换机台后旧监听仍被触发 |
| 代码评审 | 内核代码里是否出现机台 ID、活动 ID、渠道、环境判断？ | `if (machineId === ...)`、`if (env === ...)` |
| 代码评审 | 事件派发是否隔离异常，命令重名是否报错？ | 一个监听器抛错使其余监听器不再执行；重名命令被静默覆盖 |

## 误用与反模式

- 内核全能化：试图囊括所有场景，内核膨胀成巨型单体；解法是只留机制，不留策略与业务。
- 组件间隐式强依赖：`import` 其他组件、访问全局单例，组合的独立性即告破产。
- 把所有能力塞进一个大组件：内核形同虚设，复用与并行开发都落空。
- 把每个资源都机械拆包：包与依赖数量失控，加载与更新变复杂。
- 把示例内核当生产内核：半注册、事件无隔离、重名静默覆盖、`teardown` 无人调用，四个缺陷在原文示例中都存在。
## 取舍与边界

- 不用：只有一两款机台、单小组时，用模块化目录加约定即可，不立内核（R2）。
- 与 02：内核是通用层，不放领域行为；与 04：内核只留机制，策略在组件或配置里；与 07：DI 是端口落地的手段之一，外部依赖经端口进入组件。
- 与 06：内核的事件机制不用于逐帧热路径，热路径用直接调用与扁平数据。
- 与 08：事件名与命令签名是契约，跨团队后按 R3 冻结。
- 与 R1：故障隔离看似增加复杂度，但为避免一个组件拖垮结算与表现，不可省。
## 可执行的检查

| 检查项 | 执行位置 | 判定标准 |
| --- | --- | --- |
| 组件间引用检查 | 提交 / CI | 组件目录之间无跨目录引用，只允许引用契约类型包；违规数为 0 |
| 内核纯度扫描 | CI | 内核目录中不出现机台 ID、活动 ID、渠道名（词表由团队维护），命中数为 0 |
| 内核契约测试 | CI | 覆盖上表七条验证用例，缺任一条不合入 |
| 依赖声明校验 | CI / 启动 | `requires` 缺失或循环即启动失败，而非运行到该步才报错 |
| 分包构成检查 | 发布 | 机台包不被其他机台包引用；包体阈值见 12（示例值，须按项目实测） |
