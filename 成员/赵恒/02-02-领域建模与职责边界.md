# 02 领域建模与职责边界

> 源自飞书文档 · 最后同步：2026-10-30

**一句话**：按「变化原因」而不是技术分层划分模块，每个业务概念只有一个权威上下文，跨上下文只经事件或防腐层交互；客户端同样要有自己的领域模型，UI 不直接解析协议 JSON。

> 层级：L2 切分 ｜ 对应痛点：策划、美术、程序、服务端联调扯皮；多项目或多款游戏复用困难；需求频繁变更导致返工 ｜ 来源：原文《领域建模与职责边界》 + 本文扩展

## 为什么需要它

联调扯皮的根源常是「同一个词，各端理解不同」：「下注」在玩法里是押注额，在账务里是一笔扣款，在活动里是有效投注。边界不清，一处规则要改多处；客户端沦为纯渲染，协议一变，几十个界面跟着改，返工与技术债随之积累。领域建模回答「系统里有什么」，职责边界回答「谁该管什么」，合起来才能让变更只落在一处。

## 核心主张

- 先问「什么原因会让它改」：变化原因相同的放一起，不同的拆开；不按 Manager、Utils 这类技术角色分。
- 同一个词在不同上下文含义不同是正常的：各上下文建独立模型，不追求全局通用的「万能类」。
- 状态变更与校验收拢在拥有信息的对象内；规则散落在 Service 里的贫血模型是返工的温床。
- 一个事务只修改一个聚合，跨聚合靠领域事件衔接，并要有对账兜底。
- 客户端有自己的领域模型：协议 DTO 只在防腐层出现，UI 组件只绑定视图模型。
## 怎么做

1. 建统一语言。列出核心名词，写明各上下文里的含义与权威数据所在。以「下注」为例（示例，按产品实际调整）：
| 上下文 | 「下注」关心什么 | 权威数据 |
| --- | --- | --- |
| 玩法与回合 | 本回合的押注额、线数与档位 | Spin 回合 |
| 钱包与账务 | 一笔待扣减或已扣减的资金变动 | 账务流水 |
| 运营活动 | 是否计入活动进度的有效投注 | 活动进度 |
| 账户与合规 | 累计投注是否触及限额 | 限额统计 |

1. 按变化原因划上下文。示例划分：玩法与回合、数学模型、钱包与账务、运营活动、商店与支付、账户与合规。按产品取舍：若产品不涉及真实资金，账户与合规可以很薄，甚至并入其他上下文。
1. 区分三类对象。实体有唯一标识（Spin 回合有回合 ID）；值对象无身份、不可变（押注额、金额，修改即替换）；聚合根是一致性的最小单元，外部只能调用它的方法。
1. 规则放进信息的主人（GRASP 信息专家）：「本回合能否再次结算」属于回合聚合，不写在 `SpinService` 里；一个模块只应有一个被改变的原因（SRP）。
1. 控制聚合粒度，一次事务只改一个聚合。回合结算与钱包入账是两个聚合，用领域事件衔接。是否允许最终一致、如何补偿与对账，由账务设计决定；若产品涉及真实资金，这属于单向门（见 01、09）。
1. 外部模型进来先翻译。客户端的协议适配层与服务端的支付适配层都是防腐层（Anti-Corruption Layer，ACL），把外部状态码、字段翻译成内部模型（端口与适配器见 07）。
1. 客户端建视图模型：协议 DTO → 防腐层 → 视图模型 → UI 组件。可选下注档位、金额格式化等展示用派生计算放在视图模型；本地计算只用于展示与交互预判，权威结果以服务端为准（见 09）。
三种视角对同一概念（以 Spin 回合为例）的建模侧重如下（本文整理）：

| 视角 | 建模侧重 | 典型失败 |
| --- | --- | --- |
| 服务端 | 业务规则与一致性：回合状态、结算、账务 | 规则散落在多个 Service，状态被随意改写 |
| 客户端 | 视图呈现与交互：可否再转、展示金额、动画所需状态 | UI 直接判断协议状态码，协议一变全面崩塌 |
| 数据分析（埋点、数仓） | 统一口径的事件与指标：投注、赢额、回合 | 各端字段各写各的，缺语义层，口径对不上 |

```typescript
// 聚合根：状态变更与校验收拢在模型内（示例；Bet、Money 为不可变值对象）
class SpinRound {
  private state: 'REQUESTED' | 'SETTLED' | 'CONFIRMED' | 'PRESENTED' = 'REQUESTED';
  constructor(readonly roundId: string, readonly bet: Bet) {}
  settle(win: Money): RoundSettled {
    if (this.state !== 'REQUESTED') throw new Error('回合不可重复结算');
    this.state = 'SETTLED';
    return { type: 'RoundSettled', roundId: this.roundId, win };
  }
}
// 客户端视图模型：UI 只绑定它，不解析协议 JSON；DTO 只在防腐层构造
class RoundViewModel {
  constructor(private readonly dto: SpinRespDto) {}
  get canSpinAgain(): boolean { return this.dto.state === 'CONFIRMED'; }
  get winText(): string { return formatMoney(this.dto.win); }
}
```

## 在 Slots / Cocos 项目里的落地

| 场景 | 做法 | 反例 |
| --- | --- | --- |
| 一次需求：调整某活动奖励规则 | 变化原因在运营活动上下文，只改该上下文；奖励入账经事件交给钱包 | 活动判断散落在转轴、结算、UI 三处，改一个规则动三个模块 |
| 「下注」「奖励」「免费次数」等词 | 术语表登记各上下文含义，命名区分（押注额、扣款金额、有效投注） | 全局共享一个 `Bet` 类，各组往里加字段 |
| 客户端界面 | Component 脚本只绑定视图模型；协议 JSON 在适配层一次性转换 | 组件里写 `if (resp.status === 1 && resp.type === 'A')` |
| Spin 回合 | 回合聚合持有 ID、押注、结果与状态，只能经 `settle()` 等方法变更 | 多处直接赋值 `round.state = ...`，状态机形同虚设 |
| 支付渠道接入 | 支付适配层把渠道订单状态翻译成内部订单状态（见 07） | 渠道状态码一路渗透到商店界面与账务 |

## 评审清单

| 评审类型 | 检查问句 | 不通过信号 |
| --- | --- | --- |
| 设计评审 | 每个上下文能否用一句话说出它的变化原因与权威数据？ | 说不清，或两个上下文都声称拥有同一份数据（如余额） |
| 设计评审 | 同名概念（下注、奖励、免费次数）在各上下文的含义是否登记在术语表？ | 同名不同义，联调时互相误解 |
| 设计评审 | 跨上下文交互是否只经事件或适配层？ | 直接读写对方存储，或共享可变对象 |
| 设计评审 | 每个聚合是否说得出它保护的不变量，且一次事务只改一个聚合？ | 说不出不变量（该聚合应删，R5）；一次事务改多个聚合 |
| 代码评审 | 状态变更是否只经聚合或实体的方法？ | 聚合之外出现 `xxx.state = ...` |
| 代码评审 | UI 组件是否只依赖视图模型，不解析协议 JSON、不比较状态码？ | 组件里出现协议字段与状态码判断 |
| 代码评审 | 外部 SDK、渠道、协议类型是否在适配层内被翻译，不进入领域与 UI？ | 玩法或界面脚本直接引用渠道 SDK 类型 |

## 误用与反模式

- 为套 DDD 提前建立大量聚合、仓储和层级：每个新概念先说出被哪个真实变化证明（R5、R2），说不出就用普通数据结构。
- 万能模型：全局唯一的 `Player`、`Bet`、`Config`，所有上下文共用，任何字段变动牵动全部。
- 贫血模型：实体只剩 getter/setter，规则全在 `XxxService`。
- 超大聚合：把玩家与其全部回合、订单、活动进度合成一个聚合，一次改动锁住全部。
- 客户端沦为纯渲染，或照抄服务端表结构建客户端状态：两头都会让协议变更扩散到全部界面。
## 取舍与边界

- 不用：原型期、单人单模块、工具脚本；只有一两条规则的上下文不必建聚合（R2、R5）。
- 与 03：内核是通用层，不承载领域行为，领域行为由组件提供。与 06：领域建模适合元层，不要硬套到逐帧热路径。
- 与 07：防腐层是适配器的升级形态，外部模型与内部模型差异大时才引入；第二个真实实现出现前不立端口（R2）。
- 与 01：边界划错是返工根因之一；是否允许最终一致属于单向门，按 R1，合规与资金安全优先于结构整洁。
## 可执行的检查

| 检查项 | 执行位置 | 判定标准 |
| --- | --- | --- |
| 依赖方向与禁止引用 | 提交 / CI | UI 目录与玩法脚本不得引用协议 DTO 或渠道 SDK 类型；可用受限导入规则或依赖检查脚本实现（按所用工具链），违规数为 0（R6） |
| 术语表与公开类型对齐 | 提交 | 跨上下文公开的类型与事件在术语表有对应条目，缺项不合入 |
| 聚合不变量测试 | CI | 每个聚合有单元测试覆盖非法状态迁移，例如重复结算被拒绝 |
| 跨上下文写入点检查 | CI | 一个上下文的数据只被其归属模块写入，其他模块的写入点为 0 |
| 变更扇出复盘 | 线上（迭代复盘） | 登记每次需求变更涉及的上下文数；持续偏高则复查边界，阈值由团队按历史设定 |
